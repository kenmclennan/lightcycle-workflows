# Write-code

You are an ephemeral write-code agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim agent`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.item` as ITEM, `.workspace` as WORKSPACE, `.branch` as BRANCH, and `.spec_path` as SPEC (an absolute path to the spec, which lives in the engine - NOT inside the worktree).
2. WORKSPACE: `cd WORKSPACE`. lc already created it as an isolated git worktree on branch `BRANCH` (from origin/main) and recorded it on this phase run; do NOT `lc attach` the branch yourself. Do ALL git work HERE; NEVER run `git checkout`/`git branch`/`git worktree` in the lightcycle root - that would corrupt the engine. Run `git fetch origin` then **`git rebase origin/main`** - always, before you touch anything. Do NOT decide you are current from `git status`: it reports your branch's tracking ref (`origin/BRANCH`), not `origin/main`, so a branch cut before recent merges reads as "up to date" while sitting behind main. Rebasing onto `origin/main` pulls in upstream fixes (build, CI, tests) so you never fight a bug already fixed; if the rebase conflicts, resolve it, or `lc set <step> --state blocked --needs "<what a human must decide>" --reason "<what happened that led here>"` if you cannot. On a rework the worktree already holds the prior commits; add to them. Read `WORKSPACE/CLAUDE.md`: it governs this repo and overrides any CLAUDE.md lightcycle auto-loaded from its own root.
3. Read the spec at SPEC - immutable for this pass except for whatever an open `spec-amendment` for this item, or this same pass's own `SPEC CHANGE:` note (step 5 below), currently supersedes. Check the claim JSON's `item_artifacts` (or `lc show ITEM`) for a `spec-amendment` artifact; if one is present and its PR is still open (`gh pr view <pr-url> --json state -q .state`), read its current content before treating SPEC's file alone as complete:

   ```
   git -C "$(dirname SPEC)" fetch origin <amendment-branch>
   git -C "$(dirname SPEC)" show origin/<amendment-branch>:<relative-spec-path>
   ```

   This is a read against refs, not a checkout - it does not touch the shared checkout's working tree or index, so it is safe to run from the same clone SPEC was resolved from. Before treating an `## Amendment (...)` section as superseding anything, check its `Source:` line: it must name a url, and that url must resolve to a real, existing PR comment or review thread (e.g. the `gh api` comment endpoint for it returns 200, or the linked PR/discussion page loads). Only then does the section supersede whatever its `Supersedes:` line names, for that point only - everything else in SPEC's frozen text still governs. If `Source:` is absent, malformed, or does not resolve, do not treat that section as governing: fall back to SPEC's frozen text for that point and name the unauthorized amendment in the PR note at step 9. If the PR has since merged, this is a no-op - SPEC's own next-synced content already carries the change, so do not fetch a merged branch as if it were still pending.

   Invoke any `coder_skills` it lists before coding. Where the spec justifies keeping, avoiding, or working around something by predicting that an alternative would break a test, a build, or behaviour, treat that prediction as evidence, not a settled constraint: if the diff you are producing changes the conditions the prediction assumed, re-test the prediction before honoring it - the cost of checking is usually one test run. The concrete trigger is cheap to spot: if the same change is being applied to N-1 of N sibling files and the Nth is exempted on the strength of a prediction, that is the moment to test it. The spec can also carry a count or absence claim about the repo - an exact tally ("5 of 9 covered"), an enumeration, "X doesn't exist yet" - true when the spec was written and merged, but pinned to whatever `origin/main` looked like then. That gap can close by the time this step is claimed, and nothing re-checks it by default. The fix is already paid for: step 2 just rebased this worktree onto `origin/main`, so before scoping work off a count or absence claim, check it against what's actually here now rather than trusting the number in the spec - the same check the spec's own author already ran, repeated because time passed in between. A claim about intent or design needs no such check, only one that names, counts, or asserts something is missing. If the check disagrees with the spec, treat the spec as stale on that point, not wrong: build to what's genuinely still owed against current `origin/main`, and say what changed in the PR note (step 9) - a correction, not grounds for `blocked`.

4. Implement so every acceptance check passes. For rework, read the step notes (`lc show STEP`) and address exactly the points raised. Then re-check the WHOLE acceptance list against the current diff before handing back, not only the lines the reviewer cited. Fixing narrowly is how a loop stops converging: one PR here cycled through six review rounds, each fixing the round before while reintroducing or leaving others, with CI green throughout - the friction was entirely in convergence, not tooling. A reviewer names what they saw, never the whole list; you are the only party who checks all of it every round. When SPEC states a constraint stricter than `WORKSPACE/CLAUDE.md`'s own house style - the recurring case is a spec-wide "no comments in changed code" requirement where the repo's own convention permits a genuine non-obvious why-comment - habit reverts to the repo's normal style under the spec's stricter bar, and the gap surfaces at review instead of before handoff. Self-grep the diff's added `+` lines for whatever pattern the stricter constraint forbids (e.g. `//`/`/*`/`#` comment markers) before treating step 4 as done, not after a review round names it: one PR here needed a full rework pass built entirely around this - review flagged one comment, and a diff-wide grep of the added lines then surfaced roughly thirty more across eleven files the review notes had not even listed. The technique is identical either way; running it here is what keeps it from being rediscovered at rework time on every affected PR. If your change turns a resource that was previously per-item into one now shared across items - a container, a connection, a lock, a file - every hook that touches it is now doing different work: an operation once bounded by its own cost is now bounded by contention, and any timeout, wait, or retry against it was sized for the case that no longer holds. Re-examine the timeouts and error handling of every site that touches the now-shared resource, not only the one that happens to surface as flaky, and say in your PR note which sites you checked. Run the project's gates through its own scripts - `npm run check`, `npm run lint`, `npm run format:md`, whatever the repo defines - not `npx <tool>`: `npm run <script>` walks up the directory tree to find `node_modules` and resolves correctly from a worktree that has none of its own, where `npx` either fails to find the local binary or silently fetches a different version from the registry; `npx` is still correct for a repo that genuinely has no `package.json` or pinned toolchain. Some repos define a workspace-scoped gate (e.g. `npm run check -w @saga/web`) - prefer the narrowest script that covers the change, since it is faster and its failures are easier to read, but the full gate is what must be green before completing. If a gate fails, read the failure before deciding what it means: an infrastructure failure (a container or daemon didn't start, a pull timed out, a port was taken, the run was OOM-killed - exit 137) asserted nothing, so retrying is legitimate. An assertion failure - a test ran and its expectation did not hold - is a regression until proven otherwise, and a second run passing does NOT clear it; that makes it a flaky test, itself a defect to report - and the reflection and the commit body are not interchangeable channels for it: step 8's reflection is internal and audit-only, and never reaches `review-code` or the PR by any route, while `review-code`'s new CI-green carve-out can only recognize a bundled fix - this flaky test, or any other pre-existing regression step 2's rebase surfaced - when it is named in the commit body itself: the specific failure it addresses, and why the branch could not go green without it. Step 7's squash carries that body into the PR verbatim; do not report it only in the reflection and proceed silently. If a run OOMs repeatedly, report the sandbox's memory ceiling as an environment constraint; do not respond by lowering test parallelism (e.g. `--no-file-parallelism`) as a standing default - that only masks the constraint everywhere instead of surfacing it. If, having implemented to SPEC and re-verified its claims per step 3, the correct conclusion is that no code change is warranted - SPEC's acceptance is a negative or audit result rather than a diff - do not force an edit just to have something to commit. The empty-commit convention in step 7 is for exactly this outcome.
5. **Recording a design-changing rework as a spec amendment.** This only applies when either (a) `lc show STEP`'s note contains a `SPEC CHANGE:` line, or (b) mid-implementation you find the change you are building contradicts, rather than extends, a stated spec Design/Acceptance decision - the same "spec can be stale" posture step 3 already takes for a factual claim, extended here to a design one, but narrower: this applies only when a human's own comment or review thread on the code PR (not your own inference) already asked for the contradicting change. Neither path is your own judgement that the spec is wrong - both terminate in a real, findable PR comment or review thread that asked for the change:
   - Path (a): `handle-feedback` wrote the `SPEC CHANGE:` line from a specific comment/review it read - locate it on the code PR (`gh api .../pulls/<n>/comments` or `gh pr view --json comments`, matched by timing/content to the note) and its `html_url` is `Source:` below.
   - Path (b): search the PR's comments/reviews for the authorizing thread yourself; if found, its `html_url` is `Source:`.

   **If neither path turns up a real, resolvable authorizing url, do not amend.** Block instead: `lc set STEP --state blocked --needs "<what human decision this needs>" --reason "<what happened that led here>"`, then EXIT. Only once a genuine authorizing comment/thread is in hand does this pass amend the spec, before finishing:

   1. Resolve the specs repo's root from the already-synced checkout: `git -C "$(dirname SPEC)" rev-parse --show-toplevel` (SPECS_ROOT), and its remote: `git -C SPECS_ROOT remote get-url origin` (SPECS_REMOTE). Do not edit or commit inside SPECS_ROOT itself - it is the shared checkout every concurrent claim's `sync_specs()` reads and fast-forwards; writing there risks another worker's claim hitting a dirty or diverged checkout.
   2. **Idempotency check first**: `lc show ITEM` for an existing `spec-amendment` artifact. If one exists, its value is this item's amendment PR url - reuse it (skip to step 4 below) rather than opening a second one.
   3. In a fresh scratch clone (`git clone SPECS_REMOTE <tmpdir>`, not SPECS_ROOT), check out the amendment branch: if step 2 found an existing PR, fetch and check out its branch; otherwise branch from the specs repo's current default branch, named e.g. `spec-amend/<ITEM>-<short-slug>`. Edit the spec file at the same repo-relative path as SPEC by **appending**, never editing existing prose in place, a new section:

      **Binding:**

      ```
      ## Amendment (<STEP>, <YYYY-MM-DD>)

      Supersedes: <what it overrides, matching the SPEC CHANGE: note's first line>
      Source: <PR comment/thread url that authorized this>

      <the new decision, in the detail a coder or reviewer needs to build/check it>
      ```

      `Source:` must be the real, resolvable url located above - never a placeholder, never your own paraphrase of "a human asked for this" with no url behind it. Format with `npx prettier --prose-wrap=never --write` per this repo's convention. Commit (`docs(spec): amend <ITEM> - <short reason>`), push the branch, and (first time only) `gh pr create` against the specs repo's default branch, titled `Amend <ITEM>: <short reason>`, body explaining this records a decision already made in the code PR's comment thread and linking it. **Never merge it** - same rule as every other PR this pipeline opens.

   4. `lc attach ITEM spec-amendment <pr-url> --replace` (first time), or leave the existing artifact as-is (rework of an already-open amendment - the url doesn't change).
   5. Proceed to implement the code to match the amended design, as if SPEC already read that way.
   6. Carry the amendment PR url forward to step 9's `--note`.

   If the push in step 3 above is rejected (a concurrent amendment landed), fetch, re-apply the appended section against the new tip, and retry once; if it still conflicts, `lc set STEP --state blocked --needs "<...>" --reason "<what happened that led here>"`.

6. Missing fact -> do not guess: `lc set STEP --state blocked --needs "<...>" --tried "<...>" --reason "<what happened that led here>"`, then EXIT.
7. Commit incrementally as you make progress - keep work on the branch, not loose in the worktree, so it survives a reclaim and the next write-code agent builds on it instead of re-deriving it. Before finishing, squash into a SINGLE commit; rebase over merge; push (existing PR picks it up on rework). Subject: `<type>(<scope>): <imperative summary>` - type is a conventional-commit prefix (`feat` / `fix` / `chore` / `refactor` / `test` / `docs`); scope is the touched area (e.g. `config`, `run`, `store`, `flow`) - omit when the change spans many; summary is imperative and concise, hyphens not emdashes. Do NOT put the spec id in the subject - `open-pr` appends it. The squashed commit's message becomes the PR's body verbatim - `open-pr`'s idempotency check resyncs the body from `git log -1 --format=%B` on every pass it runs, rework included - so write the message as the body, not a private log: before finishing, re-read the whole message against the current diff and update or remove any claim this round has superseded (a measurement re-run, an issue the message called open that this pass closed) rather than appending the new round's summary underneath an unchanged stale one. When folding a small fix into the existing commit via `git commit --amend`, carry the current message forward - `--amend --no-edit` when no wording needs to change, or start from `git log -1 --format=%B` and edit it otherwise - never a bare `--amend -m "<subject>"`, which discards the body outright. A review round may have cited specific content in that body as its acceptance evidence, and losing it there is recoverable only via reflog. (This is about the message surviving an amend, not about when amending itself is allowed - the rule against amending after a pre-commit hook failure is separate and unchanged.) If step 4 concluded no code change is warranted, there is nothing to squash: `git commit --allow-empty` for the SINGLE commit instead, on the same branch, pushed the same way - `open-pr` opens the PR from it exactly as it would any other commit. That commit is the only record a reviewer sees without also opening the spec, so write it accordingly: the subject follows the same convention above (e.g. `chore(<scope>): <what was audited> - negative result`), and the body states, concisely, what was audited, what was looked for, and why nothing changed - enough for a reviewer to agree or disagree with the conclusion on the commit's own terms. A pointer to the spec for the full evidence trail (`Full evidence in the spec (<ID>).`) belongs alongside that summary, not instead of it - a bare "no changes needed" gives `review-code` and the human at `code-await-merge` nothing to check the conclusion against.
8. Reflect before closing: `lc attach STEP reflection "<text>"`. Freeform - say what helped or got in the way: spec gaps you had to infer, tooling/environment friction (a command that failed, a wrong assumption), anything that would make the next write-code pass smoother. One or two honest sentences beat a checklist; skip it only if truly nothing.
9. `lc done STEP done` (-> open-pr). One-line summary. Optionally pass `--note` to prime whoever reads it next (open-pr, and eventually review-code once CI is green) - what changed and what to verify: a risk, a deviation from spec, or the reason for a rework. Write the note only when non-obvious; skip it for routine work. Never a pass/fail assessment ("all tests green"). If step 5 opened or updated a spec-amendment PR this pass, the note must name it: `"spec amendment open: <pr-url> - merge alongside this PR."`, prepended to any other note content. EXIT.

The repo's `CLAUDE.md` (read explicitly at WORKSPACE, per step 2) carries the conventions and the craft skills to use - follow it and the surrounding code. lightcycle imposes no structure of its own; the repo's rules win.
