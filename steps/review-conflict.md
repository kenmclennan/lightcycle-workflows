# Review-conflict (you + driver)

`resolve-conflict` tried to reconcile this item's branch with `BASE_REF` and escalated - either a semantic conflict it should not guess at, or a rebase whose tests kept failing after repeated attempts. A human finishes what the agent could not.

`review-conflict` only routes onward on `resolved` - closing it any other way, or leaving it as the item's only open step, ends the item outright rather than re-entering the PR/CI cycle.

1. Read the claim's `inputs.previous.report` - if `resolve-conflict` escalated, it explains what is ambiguous or what kept failing after a prior rebase attempt. If this step opened instead because the PR's own conflict-retry cap was hit directly, `inputs.previous` is `null` or carries no report - check the PR's conflict markers on the branch itself.
2. The item's branch is already checked out in its own worktree (`.worktrees/ITEM` in the target repo). `cd` there, `git fetch origin`, apply the sync block below, then `git rebase BASE_REF`. **Resolve the base branch.** Right after `git fetch origin`, run `git remote set-head origin --auto`, then let BASE_REF be the output of `git symbolic-ref --short refs/remotes/origin/HEAD` (it prints `origin/<the repo's default branch>`). If either command fails, park rather than assume a branch name: `lc set STEP --state waiting --needs "the default branch of origin could not be resolved: <the git output>" --reason "<what the resolution found>"`, then EXIT. BASE_REF is used throughout this step, including in text before this paragraph. Wherever this step diffs, merges, counts behind or rebases against the base, it uses BASE_REF, never a literal branch name. **Sync to the PR's remote head.** Right after `git fetch origin`, bring the local branch to the remote head before reading or writing anything. If `git rev-parse --verify -q origin/BRANCH` prints nothing, no remote branch exists yet (before a first push): do nothing. Otherwise, if `git branch --show-current` is not BRANCH, run `git checkout BRANCH` first (a stack pass can leave the worktree on a layer branch, and the reset below would move that layer onto the top one). Then let REMOTE be `git rev-parse origin/BRANCH` and LOCAL be `git rev-parse HEAD`. If they are equal, do nothing. If `git cherry origin/BRANCH HEAD` prints any line beginning `+`, the local branch holds commits the remote lacks - this pass's own unpushed work: do nothing. Otherwise the local branch is stale (the engine rebased or advanced the PR remotely). If `git status --porcelain` is empty, run `git reset --hard origin/BRANCH` and name LOCAL and REMOTE in the step's closing note. If it is not empty, park: `lc set STEP --state waiting --needs "local BRANCH is at LOCAL, origin/BRANCH is at REMOTE, and the worktree has uncommitted changes in <the dirty paths>; commit or discard them, then re-run" --reason "<what the sync found>"`, then EXIT - never reset over uncommitted work. From here on REMOTE is the head SHA for every judgement this step makes.
3. Reconcile any conflicts by hand, preserving both sides' intent - the same discipline `resolve-conflict` itself follows. Run the repo's own test command to confirm the rebase is clean (read it from the repo - its CI workflow, README, or build file - never from memory).
4. Decide:
   - **Resolved** - force-push the rebased branch (`git push --force-with-lease`; over a stack, push as the stack-rework rule below instead, and a refused lease means re-fetch and begin again at step 2), then `lc done STEP resolved` - re-enters the PR/CI cycle the same way `resolve-conflict`'s own `resolved` outcome does.
   - **Abandon** - the conflict is not worth resolving, or the underlying change should not land - `lc done ITEM abandoned`, the item-level close, which also closes this step; do not additionally run the `resolved` outcome above.
   - **Leave it blocked** for a later look - `lc set STEP --state waiting --needs "<what a human must decide>" --reason "<what happened that led here>"`, then EXIT.

**gh stack lock.** `gh stack` runs one operation per repository at a time, and its lock lives in the repository's shared git folder, so another item in the same repository can hold it. When a `gh stack` command fails with "another process is currently editing the stack", nothing is wrong with this item: wait 30 seconds and run the same command again, for up to 5 minutes, before treating it as a failure. Never run `gh stack rebase --abort` or delete a lock file to get past it.

**Stack rework.** When the item's `delivery` entry reads `Decision: stack`, a push over the stack follows this and nothing else. After `git fetch origin`, record `SHA=$(git rev-parse origin/<layer-branch>)` for every layer before changing anything. Check out the layer a finding names; a CI failure or a test broken by the stack names no layer, so fix it on the lowest layer whose diff introduced it, never only on the top layer. Commit the fix there, then cascade the layers above with `gh stack rebase`: resolve each conflict and continue with `--continue`. After the cascade, run the repo's own tests on each rewritten layer, bottom to top, before pushing. Push each rewritten layer, bottom to top, with `git push --force-with-lease=<layer-branch>:<SHA>`, keeping any commits others pushed in the rebased history. A refused push means someone pushed in between: stop, push nothing further, and end the step by its own rule for a refused lease (never park for it). Never use `gh stack push` or `gh stack sync`: they force-push without a lease.

The `--note` on `lc done` and any `--needs` or `--reason` text you park with are read by a human or the next agent. They follow the standard below.
