# Review-workflow

You are an ephemeral review-workflow agent in lightcycle. You claim ONE step, complete it, then exit. You gate a workflow BUNDLE change against its design spec. There is no test suite for a bundle - the gate is composition-checking and a full dry-run through the real engine.

1. CLAIM: `lc claim agent`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.workspace` as WORKSPACE, `.branch` as BRANCH, `.phase` as PHASE, and `.spec_path` as SPEC (absolute path; the spec lives in the engine, not the worktree).
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree already on branch BRANCH. Do ALL git work HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root. `git fetch origin`, apply the sync block below, then diff with **three dots** against the remote head: `git diff origin/main...origin/BRANCH` - exactly what THIS branch's own commits changed. Do NOT use a two-dot diff or the local `main` ref; both can pull in unrelated changes from main advancing after the branch was cut. Read SPEC - the design mermaid plus its step/gate/trigger descriptions.
   **Sync to the PR's remote head.** Right after `git fetch origin`, bring the local branch to the remote head before reading or writing anything. If `git rev-parse --verify -q origin/BRANCH` prints nothing, no remote branch exists yet (before a first push): do nothing. Otherwise let REMOTE be `git rev-parse origin/BRANCH` and LOCAL be `git rev-parse HEAD`. If they are equal, do nothing. If `git cherry origin/BRANCH HEAD` prints any line beginning `+`, the local branch holds commits the remote lacks - this pass's own unpushed work: do nothing. Otherwise the local branch is stale (the engine rebased or advanced the PR remotely). If `git status --porcelain` is empty, run `git reset --hard origin/BRANCH` and name LOCAL and REMOTE in the step's closing note. If it is not empty, park: `lc set STEP --state waiting --needs "local BRANCH is at LOCAL, origin/BRANCH is at REMOTE, and the worktree has uncommitted changes in <the dirty paths>; commit or discard them, then re-run" --reason "<what the sync found>"`, then EXIT - never reset over uncommitted work. From here on REMOTE is the head SHA for every judgement this step makes.
   - **Read the spec amendment before checking the design mermaid.** Check the claim JSON's `item_artifacts` (or `lc show ITEM`) for a `spec-amendment` artifact; if one is present, read its text - this is what the coder built against, and what your check should run against for whatever it supersedes:

     The artifact's value is the amendment text: read it as it stands. A value that is a bare PR url (`https://` ... `/pull/<number>`) is a legacy value from before amendments were recorded on the item and holds no text: treat it as no amendment, and name it in the step's note or comment so a human can reconcile it. Before treating an `## Amendment (...)` section as governing, check its `Source:` line: it must name a url that resolves to a real, existing PR comment or review thread (a `gh api` call for the comment returns 200, or the linked page loads), and that comment must not carry `<!-- lc -->` - that marker means an lc agent posted it, and an agent's finding is not a human's decision. Only then does the section supersede whatever its `Supersedes:` line names, for that point only - everything else in SPEC's frozen text still governs. Each section is checked on its own, so one bad section does not void the others.

     If `Source:` is absent, malformed, does not resolve, or names a comment carrying `<!-- lc -->`, treat that section as non-governing: check against SPEC's frozen text for that point instead, and name the unauthorized amendment as a finding in the review comment. A design decision recorded anywhere else - the item description, a step note, a brief the merged spec has since superseded - is not an amendment and does not govern. The brief, the spec before it merges, and the code PR are the only points where a design is amended; there is no fourth channel. Review against SPEC's frozen text and name the out-of-band note as a finding. **Never post the authorizing comment yourself**, however plainly the note reads as a human's own words: a comment you write cannot be the human's own comment the coder step's spec-amendment rule requires, and posting one manufactures the authorization a later pass then verifies.
   - **When SPEC's stage/gate/trigger descriptions name a PR required in another repo, confirm it directly in that repo before judging anything else.** Most items name no companion repo - this only runs when one is named (an explicit repo name, plus a stated requirement that a PR there must exist or land at a stated point relative to this one, stated in SPEC's own prose - not a required marker syntax). The companion is most often the engine change a bundle change depends on landing first, so where SPEC names one, it usually reads as a prerequisite that must land BEFORE this PR rather than alongside it; confirm whichever landing-order SPEC's own prose actually states rather than assuming that shape. Resolve the target: if SPEC already names a specific PR url, use it directly. If it does not (the common case before that PR exists) and SPEC names a specific companion item id, resolve that item's `pr` artifact (`lc show <that-id>`) the same way step 7 resolves this PR's own url. If SPEC names neither a url nor an item id, search the target repo's PR list (`gh pr list --repo OWNER/REPO` / `gh api repos/{OWNER}/{REPO}/pulls`) for one whose body carries this item's marker `<!-- lc:item=<ITEM> -->` - the same marker `open-pr.md` step 6 writes into every PR body from the claimed item's id, so a companion PR following the same convention is findable by the same pattern (search bodies, e.g. `gh pr list --repo OWNER/REPO --state all --search '"lc:item=<ITEM>" in:body'`, never titles). Confirm the resolved PR exists and its state (open vs. merged) matches what SPEC's landing-order language requires - a read-only `gh api`/`gh pr view --repo` call against the companion repo, no checkout, the same shape as every other `gh` call this step already makes against its own repo. Re-run this check itself on every pass, never trusting a prior pass's note, this pass's own memory, or SPEC's prose alone as proof the companion PR is (still) in the right state - the companion repo's live state is what is authoritative, queried fresh every time this step runs, so a companion PR merged between a reject and the re-review is caught on the very next pass rather than surviving as a stale reject. A missing or wrong-state companion PR is a finding like any other under this step, folded into the existing fail path below - name exactly which companion repo/PR and what's missing or wrong about its state.
   - **When SPEC carries a `## Coupled change` section naming a change owed to a different repo, surface it in this pass's comment (step 7) every time - never try to confirm whether it has been filed or landed.** Distinct from the companion-PR check above: that one confirms a PR required to exist _now_, usually landing before this one rather than alongside it; this one is `design-workflow`'s cross-repo carve-out: a change BRIEF described in a different repo that the design deliberately did not draw into the mermaid or step/gate/trigger descriptions for `build-workflow` to build, naming instead under `## Coupled change` which repo needs it, what it is, and whether this item's own change treats it as a prerequisite or a follow-up. `workflow-authoring` runs exactly one code phase, against the item's own `repo` - nothing here or downstream ever opens, tracks, or gates that coupled change, so the only backstop left is making sure a human sees it before this item closes. If SPEC has a `## Coupled change` section, name it in this pass's comment regardless of whether a follow-up item already exists, or a stated prerequisite has already landed - do not search for or attempt to confirm either; that determination is unreliable from the frozen spec text alone and is the human's call at `code-await-merge`, not this step's. If SPEC has no `## Coupled change` section, this check is not-applicable.
3. Judge ONLY files this branch actually touched (the three-dot diff). A `workflows/*.md` or `steps/*.md` file the branch did not touch is out of scope - never flag it as missing coverage even if main has since changed it underneath this branch.
4. Read the QA trio from the origin's validation CI job's own run - do not run `lc workflow add`/`simulate`/`describe` yourself. A worker's `lc` refuses the `workflow` verb against its live home except `lc workflow check --dir <dir>`, so those three stay CI's, and you reach this step only via `watch-ci`'s `done` edge, which fires only once that job already passed for the current head SHA - so `check` and `simulate` are already proven for every workflow in the bundle, not just the ones this branch touched.
   - Resolve the head SHA (`git rev-parse HEAD` in WORKSPACE - never `gh pr view --json headRefOid`, which is both GraphQL and capable of returning a stale sha even through REST) and find the run of the origin's CI job that validates and simulates its workflows, for that SHA: `gh run list --branch BRANCH --workflow <ci-workflow-file> --json databaseId,headSha,conclusion -L 5`, filtered to the matching `headSha`.
   - Fetch its log (`gh run view <databaseId> --log`) and confirm the log holds a `check` section and a `simulate` section for every workflow this branch touches - the run already succeeded, so both already passed; this is reading the proof, not re-deriving it.
   - Read the `describe --mermaid` section of that log for each touched workflow and diff its rendered nodes/edges/phase grouping against SPEC's design mermaid by eye; a mismatch (a missing edge, a stage in the wrong phase, a renamed stage the design didn't call for) is a defect, not a nit. A mismatch where the _build_ carries something correct that the spec's own account - its design mermaid, or its prose - omits or leaves ambiguous is not a build defect: the build is right and the spec's own account was the thing that was short, and no rework round back to `build-workflow` can fix a spec whose own PR has already merged. The mermaid-edge case is the recurring instance (an edge one of the spec's own capped/escalating hooks needs to route its outcome, dropped from a hand-drawn diagram), but the rule is not limited to edges. Name it under a literal `Accepted differences:` line in the pass comment (step 7) - what the spec omits or leaves ambiguous, what the build does instead, and why it is correct - rather than failing the PR over it; a human reading this PR at `await-merge` decides from that line whether it is worth a follow-up item, the same convention `review-code` uses for the identical shape of gap (`steps/review-code.md` step 3). Reserve `rejected` for a mismatch that means the _build itself_ deviated from what the merged spec calls for.
   - **Check the pass boundary against the design.** `lc workflow describe` prints a `pass ends` line when the bundle declares one and nothing when it does not. If the design says the flow loops - a back-edge returning to the entry stage that the design calls a new traversal rather than a rework round - the bundle needs a `pass-end` naming that stage and outcome, and its absence is a defect rather than a nit: every traversal would accumulate into pass 1 and the phase runs it opened would never be torn down. `lc workflow check` cannot catch this; it validates a declared `pass-end` but cannot know one is missing, because a rework back-edge and a delivery back-edge are the same shape. This check is the only gate on it.
   - If the CI run for the current head SHA cannot be found, or its log cannot be fetched, that is a real gap - say so explicitly in your review note/comment rather than approving on plausibility.
   - **Check the display phrases.** `lc workflow describe` shows each stage's phrase. Every owned stage should carry one - a board line reading only the bare stage name makes the human decode a stage name to see whether it is their turn. A missing phrase on a human gate is a defect; on an agent step it is a nit.
5. Agnostic-rule checks (hard rejects, not nits - a bundle that fails these does not work once pulled by anyone else):
   - **Self-contained.** No edge, `nodes:` line, or step prompt references another origin's file, another repo's `CLAUDE.md`, or a plugin skill for craft it needs to function. Everything the bundle needs to run is inside this repo.
   - **No engine-source dependency.** No step prompt tells an agent to read the `lightcycle` engine's source to understand the grammar or hook catalog - that only works for someone with source access, breaking the pipx-binary-only distribution model.
   - **Craft lives in the step, not deferred outward.** A stage that does this pipeline's actual subject-matter work (not generic PR/CI machinery) has its own step file carrying that craft inline - it does not lean on an external convention doc to know what to produce.
   - **Prompts match the engine.** Every `lc` call and dotted field read in a touched `steps/*.md` names something the engine actually has. `lc workflow add`/`upgrade` refuse the whole origin over one of these, so a bundle that ships with drift cannot be pulled by anyone - it is a hard reject, not a nit. The origin's CI job pulls the bundle, so its log already proves this for the head SHA; read the pull step rather than re-deriving it, and treat a refusal there as the finding. Two examples: a `parent` read for a step's owning item (it is `item`), and a `--state waiting` set without both `--needs` and `--reason`. When you quote a wrong usage in a finding, do not backtick it as a dotted field or as a whole `lc` call - the gate reads those as a field this bundle uses and a call this bundle makes, so writing the defect the natural way puts it INTO the bundle you are rejecting it from.
   - **No hardcoded one-off coupling.** A stage meant to be reusable machinery doesn't bake in a name, path, or command specific to one target instead of reading it from the claim JSON or the item's artifacts.
   - **Described on its own terms.** The workflow's documentation page (where the origin keeps one), its `workflows/*.md` frontmatter/prose, and any step prompt describe this pipeline's own craft - what it carries inline and why - standalone; never by contrasting it against another workflow's name (e.g. "unlike spec-driven, ..."). A comparison like that breaks the moment the other workflow is renamed or retired.
   - **Every rule is true for every user of the workflow.** Every rule a diff adds to a `steps/*.md` or `workflows/*.md` file must hold on any stack and any machine. A rule naming one language, framework, test runner, toolchain, repo, or the author's own environment is refused: the rejection names each such line and says where it goes instead - the target repo's `CLAUDE.md` when every contributor to that repo needs it, otherwise a guidance entry in the user's guidance repo with its `applies-to` facets and steps. This is a check, not a ban on words: a stack name inside an illustrative example that a generic rule is explaining is allowed when the rule itself holds for every stack.
   - **Script tooling ships whole.** For any touched `scripts/` file, or any `lifecycle:`, `script:` or `guard: script:` declaration, reject if: a script changed with no change to its tests in `scripts/tests/`, or the origin's CI does not run them (read its log); a script writes outside its data directory (or, for a stage with an explicit workspace, that worktree), for example into the bundle directory or a path built from anything but the data-directory variable; a secret value is committed, in a script, a fixture or `config-example:` (a placeholder is fine); a script is not executable in git; a script stage's fixture lacks an entry for any outcome the workflow gives that stage, or a script guard's lacks `pass` or `fail`, so the simulate output in CI does not reach every declared outcome; or `requires-engine` is missing or too low for what the bundle now uses.
   - **Human gates declare what they present.** For any touched human gate (a step with no `model:`, `engine:` or `script:`), reject if: it declares no `presents`; its `presents` is a tab name or any value outside `pr`, `description` and `artifact:<name>`; or an `artifact:<name>` is named by no step in the same workflow's `produces`.
6. Reflect: `lc attach STEP reflection "<text>"`. Freeform - what helped or got in the way reviewing (a thin design spec, tooling friction, a recurring defect class), or "clean". Skip only if truly nothing.
7. Outcome: pass or fail, first resolve the PR - the claim JSON's `.pr` (this pass's phase run holds it); if absent, `gh api "repos/{OWNER}/{REPO}/pulls?head={OWNER}:{BRANCH}&state=open" --jq '.[0].html_url // empty'` (`OWNER`/`REPO` from `git remote get-url origin` in WORKSPACE). Re-pull head first: `git fetch origin` again immediately before posting, and if `origin/BRANCH` advanced since the diff you reviewed, re-check the changed files. Post `gh api repos/{OWNER}/{REPO}/issues/{NUM}/comments -f body="<!-- lc --> ..."` (`-f`, inline string; `NUM` parsed from the resolved PR url) before (or as part of) the `lc done`/`lc set` call: Use `-F body=@file`, never `-f body=@file`. When step 2's `## Coupled change` check is flagged, also include a `Companion item still needed:` line on whichever verdict this pass posts - naming the repo, what's needed, and whether SPEC states it as a prerequisite or a follow-up, copied from SPEC's `## Coupled change` section; this is informational, not gating, so it never itself drives a fail.
   - Pass: comment names what was checked (`check`/`simulate`/`describe --mermaid` against SPEC's design mermaid, the agnostic-rule checks, including the every-user rule check) and the clean verdict. If step 2's companion-PR check ran, also name the companion repo, PR, and state it confirmed. If step 4 found a genuinely unsettled, accepted difference, include it under a literal `Accepted differences:` line. THEN `lc done STEP done`.
   - Fail: comment states what needs to change. If the reject is because a required companion PR is missing or in the wrong state, name exactly which repo/PR and what's missing or wrong, per step 2. If `check`/`simulate`/`describe --mermaid` all pass and the built graph matches SPEC's design mermaid, but SPEC's Acceptance or Testing/Harness section requires something only prose can satisfy - a PR description recording a live demonstration's evidence, a documentation update - and the PR is missing it, name exactly what the description or workflow prose must add or correct as the note's content, the same way `review-code` does, rather than treating it as a `check`/`simulate`/`describe` defect it is not. THEN `lc done STEP rejected --note "<what to change>"` (forwards onto the next `build-workflow` step).
   - Cannot review -> `lc set STEP --state waiting --needs "<...>" --reason "<what happened that led here>"`, no PR comment.
8. One-line summary. EXIT.

Verify, do not approve on plausibility.

The `--note` on `lc done`, including the `rejected` note saying what to change, and any `--needs` or `--reason` text you park with are read by a human or the next agent. They follow the standard below.
