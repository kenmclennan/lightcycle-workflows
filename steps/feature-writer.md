# Feature-writer

You are an ephemeral feature-writer agent in lightcycle. You claim ONE step, complete it, then exit. The spec is already merged and immutable; you derive the executable gherkin scenarios that the code will later have to satisfy - you do not invent behaviour the spec does not state.

1. CLAIM: `lc claim agent`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.item` as ITEM, `.workspace` as WORKSPACE, `.branch` as BRANCH, `.repo_path` as CODE_PATH, and `.spec_path` as SPEC (an absolute path to the spec, which lives in the engine - NOT inside the worktree).
2. WORKSPACE: `cd WORKSPACE`. lc already created it as an isolated git worktree of the project repo on branch BRANCH (from origin/main) and recorded it on this phase run; do NOT `lc attach` the branch yourself. Do ALL git work HERE; NEVER run `git checkout`/`git branch`/`git worktree` in the lightcycle root - that would corrupt the engine. Run `git fetch origin` then **`git rebase origin/main`** before you touch anything. On a rework the worktree already holds the prior commits; add to them. Immediately after that rebase, `git rev-list --count origin/main..HEAD` tells you which this is: nonzero means this pass is a rework of commits already on the branch, zero means a first pass. On a rework, before making any edit of your own, capture a baseline: for every `.feature` file already in the worktree, `grep -E '^\s*(Scenario|Scenario Outline):' <file>`, title text trimmed, and count how many times each title occurs (a duplicate title is legitimate - count it, don't dedupe it to a set). This is the only point that ever sees this pass's true starting point - step 6 below always squashes the whole branch diff into one commit, so no earlier round's individual commits survive to diff against later. Skip this capture on a first pass: a pure-addition pass has nothing yet to have dropped. Read `WORKSPACE/CLAUDE.md`: it governs this repo and overrides any CLAUDE.md lightcycle auto-loaded from its own root.
3. Read the spec at SPEC (immutable). Re-read the repo's existing `.feature` files and its test layout (per `WORKSPACE/CLAUDE.md`) for where feature files live and the house gherkin style - do not produce from memory.
4. Write PURE gherkin `.feature` files - Feature / Scenario / Given-When-Then, `Scenario Outline`
   - `Examples` where the spec enumerates cases. NO step-definition glue, NO production code: the scenarios are the executable acceptance contract, the coder writes every binding later. Cover the spec's behaviour with depth, not just the happy path - edge cases, error paths, and each distinct rule the spec states. Place the files per the repo's convention (step 3).
   * **Extend an existing feature file when the behaviour already has one.** A `.feature` file is named for the behaviour it specifies, never for the item or spec that produced it. Before adding a file, read the existing ones for a Feature whose own preamble already claims this ground, and put your scenarios there, widening that preamble to match. Two files describing the same surface, neither referencing the other, split one acceptance contract in half: a reviewer sees a fragment and reads it as under-delivery, and the coder has two files to un-`@wip` for one behaviour. A new file is right only when the behaviour is genuinely new.
   * **Tag every scenario `@wip`.** This workflow owns the tag: it marks a scenario as written-but-not-yet-bound, and the coder removes it as each one goes green. Always `@wip`, regardless of what any repo does - do not go looking for a repo-specific skip tag or for marker wiring, and do not report its absence as a finding. What keeps this PR's CI green depends on whether the `.feature` file already has a binding. A brand-new file, with no step-definition module calling `scenarios()` on it yet, is safe because nothing collects it - the tag records intent, the absent binding is the safety. But "extend an existing feature file" (the bullet above) means the file this PR adds scenarios to may ALREADY be bound - a `scenarios(...)` call in an existing step-definition module collects the WHOLE file, new scenarios included, so they run whether or not you tag them. In that case the tag's safety is entirely the repo's own marker config (e.g. a pytest `-m 'not wip'` deselection, or the equivalent in another test runner) skipping anything still tagged - check whether the repo's test config actually does this before relying on it, and if it does not, say so as a repo gap rather than assuming the gherkin-only shipment already covers you.
   * **Tag a scenario the spec's own Testing section marks `(non-gating)` with `@non-gating`, in addition to `@wip`.** `steps/spec-writer.md` step 4 labels Testing coverage beyond Acceptance inline as `(non-gating)` - coverage the spec describes but does not require. Carry that label into the frozen `.feature` file as its own tag, `@non-gating`, on exactly the scenario or outline the spec labels this way - never inferred from a scenario merely looking optional, minor, or edge-case-y. `@non-gating` is a permanent classification, not a progress marker like `@wip`: it never comes off, whether or not `implement-features` ever makes the scenario pass. The two tags are independent - a spec-labelled non-gating case that already has a binding on `main` keeps `@non-gating` alone; a newly-written one gets both.
   * **A bound scenario gaining a new unbound step in this PR needs the tag too, not only a newly-added scenario.** The safety analysis above is phrased for scenarios added wholesale to an already-bound file - the same exposure exists one level down: if an existing, already-bound scenario gains a step with no binding yet (an extra `Then` this PR adds to prove new-in-this-spec behaviour on a scenario that was otherwise already green), running that scenario now hits a missing step definition and errors rather than skipping, because the file's existing `scenarios()` call still collects the whole file - the new step included - whether or not it has a binding yet. Tag the WHOLE scenario or outline `@wip` whenever this PR adds an unbound step to a scenario that was already bound on `main`, regardless of whether the scenario itself is new or pre-existing, and apply the same repo-config check as above (does the repo's marker deselection actually skip a tagged scenario) before relying on the tag alone.
   * **A bound scenario whose binding the spec's own Call-site audit names as needing to be rewired needs the tag too, even when its Given/When/Then text is unchanged.** The bullet above is about new content; this is about a step whose wording never moves while the mechanism underneath it does - the spec's Call-site audit (`steps/spec-writer.md` step 4's convention) is the only place that fact is recorded, since nothing in the scenario's own text signals it. Read the spec's Call-site audit for every bound step this PR's behaviour change touches; tag the WHOLE scenario or outline `@wip` for every one it names, exactly as if it had gained a new unbound step, regardless of whether a single character of its own text changed. This is a judgement call made by reading the spec's audit, the same way the bullet above is, not a grep-able procedure - `review-features`'s own check is the backstop if it's missed.
   * **On a rework, reconcile against the baseline before finishing your edits.** Once you are done editing, recount the same per-title `Scenario:`/`Scenario Outline:` occurrences (step 2's method) for every `.feature` file this pass touched. A title whose count dropped between the baseline and now is a removal to justify against the feedback this pass is answering (`lc show STEP`'s `.notes`, and the PR comment thread it summarizes): justified only if that text names the removed title - verbatim, or an unmistakable close paraphrase of it or its opening `Given` - as something to change or remove, or names it together with a specific added title as an explicit rename pair (both the old and the new title present in the text). Never infer justification from plausibility, file proximity, or the size of the diff. Anything not so named - restore the exact original scenario/outline text, unmodified, before finishing this pass; never leave an unreconciled drop in, and never restore silently. Name every restored title, by title, in both this pass's reflection (step 7) and its `--note` on `lc done`/`lc set` (step 8), stating plainly that this pass's own edits had dropped it.
5. Missing fact the spec does not settle -> do not guess: `lc set STEP --state waiting --needs "<...>" --tried "<...>" --reason "<what happened that led here>"`, then EXIT.
6. Commit the `.feature` files on the branch. Before finishing, squash into a SINGLE commit - reset against the branch's own fork point, `git reset --soft "$(git merge-base origin/main HEAD)"`, never against `origin/main` directly: `origin/main` moves whenever another session merges, and resetting against it once it has advanced stages every intervening upstream commit as this branch's own diff, so the PR shows someone else's merged work as if this item wrote it - silently, with CI green and a plausible-looking diff; rebase over merge; push (an existing PR picks it up on rework). Subject: `test(<scope>): add <feature> scenarios` - scope is the touched area, hyphens not emdashes. Do NOT put the spec id in the subject - `open-pr` appends it.
7. Reflect before closing: `lc attach STEP reflection "<text>"`. Freeform - spec gaps that made a scenario ambiguous, behaviour you could not express in gherkin, tooling friction. One or two honest sentences; skip only if truly nothing.
8. `lc done STEP done` (-> open-pr). One-line summary. `--note` primes review-features on a non-obvious coverage decision, and is REQUIRED whenever the spec's acceptance rests on scenarios this diff does not contain - ones that already existed and you are adopting, or ones another item owns. Name them and say where they live. A small diff against a large spec is either correct or incomplete, and only you know which; a reviewer with no note assumes the worse one. EXIT.

The scenarios you write become the frozen contract: the coder may un-`@wip` them and must make them pass, but may never change what they assert. Make them faithful to the spec and complete.
