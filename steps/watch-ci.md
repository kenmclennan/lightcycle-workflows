# Watch-CI

You are an ephemeral watch-ci agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim agent`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.item` as ITEM, `.workspace` as WORKSPACE, `.branch` as BRANCH, and `.pr` as the PR url (this pass's phase run holds it).
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree on branch `BRANCH`. Run all git/`gh` HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root. Read `WORKSPACE/CLAUDE.md`: it governs this repo and overrides any CLAUDE.md lightcycle auto-loaded from its own root.
3. `lc show STEP` for the pointer note `poll-ci` (engine) forwarded when it routed here: which run concluded and, on failure, the failing check's name. `poll-ci` already polled checks for the current head SHA and completed itself once CI concluded - this step never polls, re-derives success/failure, or waits on anything; it acts on the conclusion it was handed. `git fetch origin`, then resolve the head SHA locally, `git rev-parse HEAD` in WORKSPACE - never `gh pr view --json headRefOid`, which per LC-405 can return a sha that lags the true branch tip even through REST. On success: skip straight to step 4 (comment staleness) and close `done`. On failure:

   e. Fetch the actual failing job/logs for the named check before doing anything else - `OWNER`/`REPO`/`NUM` parsed from the PR url (`.pr` on the claim JSON, matching `https://github.com/{OWNER}/{REPO}/pull/{NUM}`), `gh api repos/{OWNER}/{REPO}/commits/{SHA}/check-runs --jq '[.check_runs[] | {name, status, conclusion}]'` (`SHA` from above) to get the run, then read its actual log; never guess from the summary line or the check's name alone. `watch-ci` has no authority to re-run CI to see if a confirmed failure clears: do not `gh run rerun` (or any equivalent re-trigger). A green result on a rerun of the same SHA is not evidence the failure was false - it is evidence the failing test is flaky, itself a defect for `write-code` to report (see `write-code.md` step 4), not grounds to conclude `done` here.

   e1. Before routing to `ci-failed`, for each check `poll-ci` named as failing, gather live evidence for whether the failure reflects a repo-wide precondition rather than this PR's own diff - without hardcoding any gate's name, and without reading `origin/main`'s recorded CI history (current or historical) for the identically-named check. A check gated on a live external precondition at run time - an env-pinned value checked against another repo's current head, for example - rather than against this repo's own commit content can stay `success` on `main` indefinitely even while every fresh run of the identical check on every other branch fails it, and a scheduled re-evaluation of that precondition on `main` can itself be wired to never produce a `failure` conclusion regardless of what it finds; no reading of `main`'s recorded history, at any commit or any time, can be trusted to surface this failure class. Test it live instead, with two tests that compose rather than short-circuit each other: corroboration establishes what kind of failure this is, and a behind-`origin/main` check establishes separately whether a fix may already be available to pull in - a corroboration hit does not, by itself, justify parking before that second question is asked. First, cross-PR corroboration: list up to the 20 most recently updated other open PRs in this repo, excluding this one - `gh pr list --repo {OWNER}/{REPO} --state open --limit 20 --json number,headRefOid,updatedAt --jq 'sort_by(.updatedAt) | reverse | [.[] | select(.number != {NUM})]'`. For each candidate, in order, read its latest run of the identically-named check: `gh api repos/{OWNER}/{REPO}/commits/{CANDIDATE_SHA}/check-runs --jq '[.check_runs[] | select(.name=="<the failing check'"'"'s name>")] | sort_by(.started_at) | last | {status, conclusion, started_at}'`. Treat an empty or erroring response for a candidate as inconclusive, not as "no failure" - skip it and continue to the next; require a zero exit code and valid JSON before trusting any `gh api` response in this step, never a substring match on combined stdout+stderr. A candidate corroborates when its read is `completed` with conclusion `failure` or `error`, and its `started_at` falls within 24 hours of this PR's own failing run's `started_at` (from clause e's own check-runs read, or refetched the same way). Stop at the first corroborating candidate found; do not additionally verify the two PRs' changed files don't overlap - two independent diffs coincidentally triggering the identical named failure at the same time is itself the evidence this test exists to read, not a case to filter out. Record the outcome - corroborated (keep the candidate's number, SHA, `started_at`, and conclusion) or not - but do not act on it yet; corroboration answers what kind of failure this is, not whether a fix is already available, which the next test checks independently. Second, regardless of what the corroboration test found: test whether this branch is behind `origin/main` - `git rev-list --count HEAD..origin/main`. If the count is greater than zero, rebase onto `origin/main`; on a clean rebase, `git push --force-with-lease`, then close this step `retried` (-> `poll-ci`, which reads the new head SHA exactly as for any fresh push) - do not conclude `ci-failed` or park for this occurrence yet, whether or not corroboration was found above; stop here, no further disposition applies for this run. If the rebase conflicts, abort it (`git rebase --abort`, leaving the branch exactly as it was pushed) and fall through to the disposition below, the same as finding nothing to retry. Disposition, once the rebase above has either found nothing to retry (`git rev-list` was zero) or conflicted: fall back on the corroboration result recorded above. If corroborated: park for a human (the "Human decision needed" path in step 6), `--needs` stating the failing check's name, this PR's own failing run's `started_at`, the corroborating PR's number, SHA, `started_at`, and conclusion, the two re-runnable `gh api check-runs` queries above (filled in with the real values), and, if a rebase was attempted, that it conflicted. If not corroborated: fall through unchanged to `ci-failed`, exactly as if this clause did not exist. When more than one check failed for this SHA, apply the corroboration test to each independently, but run the rebase-and-retry at most once for the whole run - a single rebase re-tests every failing check together. If that rebase pushes cleanly, close `retried` for the run as a whole, regardless of individual corroboration results. If it does not run (already level with `origin/main`) or conflicts, reach the disposition above once for the run as a whole: take the park-via-corroboration path only if every check still failing has its own independent corroboration, otherwise fall through to `ci-failed` for the whole run instead. This step is re-claimed fresh each time `poll-ci` routes back here, so the rebase-retry naturally runs at most once per claim, with no counter needed - across `N` rework rounds it can fire up to `N` times total for the same item, not once overall. This is bounded by `ci_failed_cap` already governing how many times the item can bounce between `watch-ci` and `write-code` in total; the retry firing does not consume a `write-code` hop, so it does not itself tighten that existing bound, but it cannot loosen it either. Corroboration lookups are read-only and are not subject to this cap - they may be attempted on every clause-`e1` evaluation.

4. Comments: before deciding correct vs wrong, check staleness against the head SHA resolved in step 3. Use the **committer** date (`git log -1 --format=%cI <SHA>`), never the author date: `git commit --amend` preserves the author date but rewrites the committer date, so on an amended branch the author date can be older than a comment the amend already addressed, and comparing against it hides that. A comment whose `created_at` predates HEAD's committer date is a candidate for stale, not automatically resolved: read the file/lines it claims are wrong against current HEAD before deciding - it may already be fixed, or it may still stand. Say which, in the reply. This is a different read of the same PR thread `review-code` step 3 reads for provenance (LC-138): a stale claim and a `<!-- lc -->` provenance reply answer different questions about a comment - checking age does not tell you provenance, and checking provenance does not tell you age. Do not conflate the two. Then: correct (including confirmed-stale) -> escalate a fix, noting that HEAD already addresses it if so; wrong -> reply refuting with evidence, citing the current SHA/committer date that supersedes the comment's claim. Never use confirming language ("queued", "fix confirmed", "done", "fixed") in a reply unless a commit implementing the fix already exists on the branch when you post it - if the fix is only escalated or deferred, say that plainly instead; a confirming reply with nothing behind it reads to the next pass as resolved state it is not.
5. Reflect: `lc attach STEP reflection "<text>"`. Freeform - friction watching the PR (CI config gaps, flaky/ambiguous checks, comment handling) or "clean". Skip only if truly nothing.
6. NEVER merge. CI green + comments resolved -> `lc done STEP done` (-> review-code). CI failed, with no rebase available to clear it -> `lc done STEP ci-failed --note "<failing job> / <failing test id(s)> / <short log excerpt>"` (-> write-code; reworks on the same branch/PR). The note must name the actual job, test, and error line - never just "CI failed" - so the next write-code agent reads the failure instead of re-deriving it. A rebase cleared a stale-precondition failure (clause e1) -> `lc done STEP retried --note "<what was behind origin/main, what rebased cleanly>"` (-> poll-ci; hands the new head SHA back to the engine to read like any other push). Human decision needed -> `lc set STEP --state waiting --needs "<...>" --reason "<what happened that led here>"`. A park reached via clause e1 should already carry a directly re-runnable --needs per that clause's own wording.
7. One-line summary. EXIT.

The repo's `CLAUDE.md` (read explicitly at WORKSPACE, per step 2) carries what the repo records about its own CI, toolchain and environment - a known interactive gate, a flaky runner, an org-specific quirk. Read it for diagnosis, not authorship: what it states is evidence when judging whether a failing check is a real defect or a known local condition, not a spec for what to build.

Never merge.
