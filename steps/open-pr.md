# Open-PR

You are an ephemeral Open-PR agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim agent`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.item` as ITEM, `.workspace` as WORKSPACE, `.branch` as BRANCH, and `.phase` as PHASE.
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree on branch `BRANCH`. Run all git/`gh` HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root. **WORKSPACE decides which repo this PR opens in, not the item's `repo` artifact.** `lc show ITEM` reports `repo` - the target project the work is ultimately for - and a phase whose workspace is a different repo opens its PR there instead: a spec phase on the `specs` workspace opens in the specs repo while `repo` still names the code project. That is the design, not drift; do not correct it, and do not report it as a discrepancy.
3. BRANCH-AUTHORITATIVE IDEMPOTENCY CHECK: the branch, not the `.pr` this phase run already carries, decides whether a PR for this phase already exists. No PR is confirmed to exist yet at this point, so resolve OWNER/REPO from `git remote get-url origin` in WORKSPACE (already local, already needed for the fetch/push below) rather than from a PR url. Look up any existing PR for this branch via REST: `gh api "repos/{OWNER}/{REPO}/pulls?head={OWNER}:{BRANCH}&state=open" --jq '.[0].html_url // empty'` (the same query step 6 uses):
   - **A PR is returned:** its head is this exact branch - treat it as existing. Run `git push --force-with-lease` to ensure the branch is current, then resync the body: parse NUM from the returned url and `gh api repos/{OWNER}/{REPO}/pulls/{NUM} --jq .body`. If it contains the `<!-- lc:body -->` / `<!-- /lc:body -->` markers written in step 6, replace only the text between them with the current `git log -1 --format=%B` and `gh api repos/{OWNER}/{REPO}/pulls/{NUM} -X PATCH -f body="<result>"` (`-X PATCH` is required - `gh api`'s default method once fields are present is `POST`, which would attempt to create rather than edit) - everything before and after the markers, including anything a human wrote there, is left exactly as it was, except that the item marker `<!-- lc:item=<SPEC-ID> -->` (see step 6) is added on its own line just before the opening `<!-- lc:body -->` if the body does not already carry it. If the markers are missing (a human replaced the body and took the markers out with it), that is a signal the body is no longer machine-owned - leave it alone. Then resync the title too, whether or not the markers were found: a rework can replace the commit subject (a redesigned fix), and the title would otherwise keep naming the rejected first round. Build the title exactly as step 6 does - `git log -1 --format=%s`, nothing appended - and, if it differs from `gh api repos/{OWNER}/{REPO}/pulls/{NUM} --jq .title`, `gh api repos/{OWNER}/{REPO}/pulls/{NUM} -X PATCH -f title="<title>"`. Then skip to step 7. Use `-F body=@file`, never `-f body=@file`.
   - **No PR is returned, and the claim JSON's `.pr` is empty:** genuinely no PR for this phase yet - continue to step 4 and open one there.
   - **No PR is returned, but the claim JSON carries a `.pr`:** this is neither "exists" nor "absent" - it is a divergence, not a case to resolve either way. A rework pass can re-mint this worktree's branch while the run's recorded PR still points at the earlier branch name. Do not silently reuse it (it is not this branch's PR) and do not silently open a new one (this phase run already has a PR somewhere, and opening another duplicates it). Instead: `lc set STEP --state waiting --needs "this phase run's recorded PR <the .pr url> does not match its worktree's branch BRANCH (the REST pulls lookup for BRANCH found nothing) - resolve the divergence before opening or reusing a PR for this phase." --reason "<what happened that led here>"`, then EXIT.
4. TIP OF MAIN: `git fetch origin`, then `git rebase origin/main`. This is the tip-of-main invariant. On a rebase CONFLICT: `git rebase --abort`, then `lc done STEP conflicted` (-> resolve-conflict) and EXIT.
5. PUSH: `git push --force-with-lease` (the rebase rewrote history).
6. Find or open the PR - NEVER a duplicate. `gh api "repos/{OWNER}/{REPO}/pulls?head={OWNER}:{BRANCH}&state=open" --jq '.[0].html_url // empty'`; if one exists, use it. Only if none exists: `gh api repos/{OWNER}/{REPO}/pulls -f title="<title>" -f body="<body>" -f head=BRANCH -f base=main --jq .html_url` (POST is the default once fields are present, per `gh help api`) targeting main, with the body set to the item marker `<!-- lc:item=<SPEC-ID> -->` (the leading id token of the item's `spec` artifact filename) on its own first line, then the commit message wrapped in a sync marker (`<!-- lc:body -->`, then `git log -1 --format=%B`, then `<!-- /lc:body -->`) - so step 3 can resync just that block on a later rework pass without touching anything a human adds around it. Title it with the branch's commit subject exactly, never appending the spec id: a squash merge uses the PR title as the commit subject, so an id in the title lands on the default branch, which a project that forbids work-item keys in its repo cannot accept. The item marker in the body carries the PR->spec traceability instead, and the commit-subject guidance not to include the id stays as is. If the create call itself errors or times out, that is NOT proof the PR was not created - the call may have succeeded server-side despite the failure. Before retrying, re-run the REST pulls lookup above; if a PR is now there, the create succeeded despite the error - use it and continue below rather than retrying. Then `lc attach ITEM pr <url>` (the returned `html_url`). The url lands on this pass's phase run, which holds exactly one PR, so there is nothing to label and nothing to replace - a later pass through the same phase is a different run and cannot resolve to this one's already-merged PR. On a rework pass this is idempotent, since step 6 reuses the existing PR for the branch and re-attaches the same url. Use `-F body=@file`, never `-f body=@file`.
7. CLOSE THE LOOP on queued rework, on every pass once the branch is pushed (step 3's existing-PR path lands here too). Read the PR's comments, review comments and reviews (`gh api` on issue comments, `pulls/{NUM}/comments` and `pulls/{NUM}/reviews`) and list every lc acknowledgement carrying `<!-- lc:decision=rework -->`. Drop each one that already has a reply in its thread carrying `<!-- lc:completes=<its comment id> -->`. Then keep only those this push contains: an acknowledgement whose `created_at` predates the writer's commit time (`git log -1 --format=%cI`), because its `<!-- lc:watched=STEP -->` step's routed rework is what produced this push. Leave any later acknowledgement unanswered, so `handle-feedback` step 3 carry-over still routes it. If none is left, do nothing. For each one kept, post one completion reply in the same thread: threaded via `gh api repos/{OWNER}/{REPO}/pulls/{NUM}/comments/<comment-id>/replies` for an inline review comment, top-level via `gh api repos/{OWNER}/{REPO}/issues/{NUM}/comments` for a top-level mention or review body. Open it with `<!-- lc -->` then `<!-- lc:completes=<acknowledgement comment id> -->`, name the pushed head SHA (`git rev-parse HEAD`, after the push), and say in one or two plain sentences what changed, drawn from the writer's commit (`git log -1 --format=%B`) and the closing note on the item's writer step (`lc show ITEM`). Check the claim against the diff (`git show HEAD --stat` and the hunks it names) before wording it. If the change this acknowledgement was meant to address was not made, or only partly, say so plainly and say what is missing. Never say "fixed" or "done" for something the diff does not contain. Post with `-f body="..."` as in step 6. Use `-F body=@file`, never `-f body=@file`.
8. Reflect: `lc attach STEP reflection "<text>"`. Freeform - friction opening the PR (rebase conflicts, force-push surprises, gh/PR issues) or "clean". Skip only if truly nothing.
9. `lc done STEP done` (-> poll-ci, or straight to a review gate for a phase with no CI, e.g. `spec-open-pr` -> `spec-await-merge`). One-line summary. EXIT.

Never merge. Never open a second PR for a branch.

Any `--needs` or `--reason` text you park with, the `--note` on `lc done`, and every completion reply posted in step 7 are read by a human. The PR title and body come from the squashed commit on every round, and are not yours to word - only to resync. They follow the standard below.
