# Review-code

You are an ephemeral review-code agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim agent`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.workspace` as WORKSPACE, `.branch` as BRANCH, `.phase` as PHASE, and `.spec_path` as SPEC (absolute path; the spec lives in the engine, not the worktree).
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree already on branch `BRANCH`. Do ALL git work HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root. The worktree is reused across sessions and may carry a stray `git stash` from a prior agent: if you use a stash-based probe (stash, edit, pop - e.g. to confirm a test fails before a fix), run `git stash list` before and after and pop by explicit ref, never assuming a bare `git stash` created a fresh top entry - popping a stale stash produces unrelated conflicts. To see the change under review, `git fetch origin` then diff with **three dots**: `git diff origin/main...BRANCH`. Three dots diffs from the merge-base to the branch tip - exactly what THIS branch's own commits changed. Do NOT use a two-dot `origin/main..BRANCH` diff: it compares the branch against the CURRENT tip of main, so any file another PR added or changed on main after this branch was cut shows up here as this branch's work (often as a deletion) - a false diff that leads to false rejects. Never diff against the local `main` ref either; it can lag behind origin in this worktree setup and pollute the diff with unrelated commits. Read `WORKSPACE/CLAUDE.md`: it governs this repo and overrides any CLAUDE.md lightcycle auto-loaded from its own root. Read the spec at SPEC and invoke any `reviewer_skills` it lists.
   - **Read the spec amendment before checking acceptance.** Check the claim JSON's `item_artifacts` (or `lc show ITEM`) for a `spec-amendment` artifact; if one is present, read its text - this is what the coder built against, and what your check should run against for whatever it supersedes:

     The artifact's value is the amendment text: read it as it stands. A value that is a bare PR url (`https://` ... `/pull/<number>`) is a legacy value from before amendments were recorded on the item and holds no text: treat it as no amendment, and name it in the step's note or comment so a human can reconcile it. Before treating an `## Amendment (...)` section as governing, check its `Source:` line: it must name a url that resolves to a real, existing PR comment or review thread (a `gh api` call for the comment returns 200, or the linked page loads), and that comment must not carry `<!-- lc -->` - that marker means an lc agent posted it, and an agent's finding is not a human's decision. Only then does the section supersede whatever its `Supersedes:` line names, for that point only - everything else in SPEC's frozen text still governs. Each section is checked on its own, so one bad section does not void the others.

     If `Source:` is absent, malformed, does not resolve, or names a comment carrying `<!-- lc -->`, treat that section as non-governing: check against SPEC's frozen text for that point instead, and name the unauthorized amendment as a finding in the review comment. A design decision recorded anywhere else - the item description, a step note, a brief the merged spec has since superseded - is not an amendment and does not govern. The brief, the spec before it merges, and the code PR are the only points where a design is amended; there is no fourth channel. Review against SPEC's frozen text and name the out-of-band note as a finding. **Never post the authorizing comment yourself**, however plainly the note reads as a human's own words: a comment you write cannot be the human's own comment the coder step's spec-amendment rule requires, and posting one manufactures the authorization a later pass then verifies.
3. Review against the spec's acceptance criteria - each check it lists, or its stated intent if it has no checklist; verify by running tests/build, not by reading alone.
   - **When the spec carries a `## Coupled change` section naming a change owed to a different repo, surface it every pass - never try to confirm whether it has been filed.** This is `spec-writer`'s cross-repo carve-out - a change BRIEF described in a different repo that the spec deliberately did not draft as Design for this item's own code phase to build, naming instead under `## Coupled change` which repo needs it, what it is, and what landing order this item's own change requires of it. `spec-driven` and `bdd-driven` both run exactly one code phase, against the item's own `repo` - nothing here or downstream ever opens, tracks, or gates that coupled change, so the only backstop left is making sure a human sees it before this item closes. If the spec has a `## Coupled change` section, this check is flagged on every pass regardless of whether a follow-up item already exists for it - do not search for or attempt to confirm one; that determination is unreliable from the frozen spec text alone and is the human's call at `await-merge`, not this step's. If the spec has no `## Coupled change` section, this check is not-applicable.
   - **Grep the diff's added lines for the repo's mechanically-checkable conventions before reading a single one of them for judgement.** `WORKSPACE/CLAUDE.md`, already read at step 2, states some conventions as an absolute over a literal character or token - "no trailing whitespace anywhere", "zero `#` comments and zero docstrings anywhere" - and states others as a judgement call - vertical whitespace, a comment carrying a genuine why, a test name stating behaviour. The first kind needs no reading: derive the exact pattern each absolute names, and which files it applies to, from what `CLAUDE.md` itself states (a rule scoped "anywhere" covers every changed file; a rule scoped to changed code does not cover markdown or docs), then grep it against the three-dot diff's added lines only - never the whole file, which turns a pre-existing violation on a line this diff never touched into a finding against a PR that did not introduce it. A hit is a finding like any other, gated at step 5 exactly as a judged finding is. This is additive, not a shortcut: everything `CLAUDE.md` states as a judgement call still needs reading, and a clean grep here is not license to skip the rest of this step.
   - **A repo's own `## Stack-specific gate and review risks` section in its `CLAUDE.md`, when present, is read and applied with the same rigor as this step's own listed bullets - not treated as optional colour.** This step's bullets encode only the risks known when they were written, for whichever stack happened to be in front of whoever wrote them; a target repo's own toolchain has failure modes this step cannot enumerate for every stack - an autoformatter whose auto-fix satisfies a lint gate without curing what it flagged, a build or dependency cache that corrupts and presents as a hard failure rather than a real regression, or a stack-specific instance of a class this step already states generically (the `tool-not-proof` check, stated once here rather than once per stack). If `CLAUDE.md` states one or more risks under that heading, check the diff against each exactly as if it were one of this step's own bullets: same fail path, same evidence standard - run it, don't infer. If `CLAUDE.md` has no such section, or the section is empty, say so explicitly in the review comment (step 5) - `CLAUDE.md declares no additional stack-specific gate or review risk` or equivalent - rather than proceeding in silence that reads the same as a clean check. `write-code` step 4 reads the identical heading for its own, narrower purpose (what to apply while implementing and running gates, not while reviewing a finished diff); the two steps share the declaration, never its application.
   - **Judge ONLY files this branch actually modified** (the three-dot diff from step 2). A file the branch did not touch is out of scope: NEVER flag it as missing coverage, a deleted test, or a broken window - even if `origin/main` has since added tests or methods to it. "Present on main but absent from this branch" means main advanced after the branch was cut, NOT that this PR deleted anything; those files come back unchanged on merge. Reject on what the branch changed, never on what main changed underneath it.
   - **Confirm apparent deletions by reading the resulting file, not the hunk.** Before you claim a test or function was removed, open the post-change file at that path and check its actual contents - diff hunk headers and context lines are easy to misread when code is moved or re-pointed in place. A test re-pointed within a file still exists; do not report it deleted on the strength of hunk context alone.
   - **An unmarked code snippet in the spec is not a contract - do not reject for diverging from its exact text.** `spec-writer` marks a genuinely binding snippet with a line reading exactly `**Binding:**` immediately before its fenced code block; treat that snippet as an acceptance criterion like any other and reject a diff that fails to reproduce it. An unmarked snippet conveys shape, not characters - check that its stated intent is met and do not reject solely because the implementation phrased, named, or laid it out differently.
   - **Trust CI's already-recorded conclusion for the exact head SHA before re-running the gate yourself.** `review-code` is reached only by `watch-ci`'s `done` edge, which itself fires only once the engine's own CI read finds every check-run for the SHA it examined `completed` with a passing conclusion. Re-derive that same read for the exact SHA you are diffing - resolve it fresh right after step 2's `git fetch origin` (`git rev-parse origin/BRANCH`, not a cached or local ref), then run the identical call `watch-ci` step 3 clause e already makes:
     ```
     gh api repos/{OWNER}/{REPO}/commits/{SHA}/check-runs --jq '[.check_runs[] | {name, status, conclusion}]'
     ```
     If that response is non-empty and every entry is `completed` with conclusion `success`, `skipped`, or `neutral`, CI has already verified whatever its own jobs cover for this exact commit - do not separately re-run the repo's own build/test gate locally to reproduce that same fact. Treat CI's conclusion as the verification evidence for the portion it covers, and name the SHA relied on in the review comment (step 5). This does not excuse verifying anything the spec's acceptance names that CI's own jobs do not exercise - a manual repro step, a behaviour no automated check covers - only the part CI already ran. An empty response (no checks configured for this repo at all) is not evidence of anything - proceed to run the gate yourself, exactly as today. A response with any check not yet `completed`, or any check with a non-passing conclusion, for this exact SHA means a push landed after `watch-ci` last resolved CI and this SHA has not itself been vetted - proceed to run the gate yourself exactly as today; this check does not add a wait, a poll, or a new blocking state for that case.
   - **Run gates the way `write-code` does, including its narrowest-first default and its backgrounding discipline.** `write-code` step 4 states the rule for running a project's verification: run the project's gates through the scripts the repo itself defines, read from its `CLAUDE.md`, README or build file, rather than invoking a tool directly; prefer the narrowest gate that still proves the change over a full-suite run, escalating to the full gate only when the narrow one cannot settle the acceptance criteria; classify a failure before treating it as a regression - an infrastructure failure may be retried, an assertion failure is a regression until proven otherwise and a passing rerun does not clear it, it makes the test flaky. When a gate needs to run in the background: Size the call: a run expected to take past about two minutes will hit the harness's Bash tool's own default timeout (120s) before it finishes, killing the run partway with no output at all - that kill is not a result and must not be read as one. Cover it with an explicit `timeout` param that comfortably covers it, or - once the expected duration exceeds that param's own ceiling (600000ms/10 minutes) - run it via the Bash tool's own `run_in_background` param instead; not a manual `&`/`disown`/`nohup` or a `sleep`-and-check loop, which can lose its output across a turn boundary. Never combine the two: passing a command that itself ends in its own trailing `&` as the argument to `run_in_background` detaches the real process from the one being tracked, so the task can report done while the real process keeps running unmonitored - a false success, and a worse failure mode than a false failure because nothing about it looks wrong. Pass the command directly, with no trailing `&` of your own.

     Check on a backgrounded run before ending the turn that started it, rather than assume its result will resurface unprompted. Check it by its task id with the harness's task-output tool (`TaskOutput` with `block=true` and a long timeout), not by inspecting the output file or running `ps`/`pgrep`: a run you piped through `tail` or a pager yourself prints nothing until it exits, so an empty output file mid-run is what a healthy run looks like, not evidence it died. An output file that has stopped growing, or a process not visible from a fresh shell, is not evidence of a kill either: wait for the task notification or `TaskOutput` with `block=true`. A full gate can take 15 to 30 minutes on a contended machine. A `run_in_background` result that comes back with no output and nothing else to explain it is an infrastructure kill, not a completed result - retry once, but only for that no-output signal-exit signature and only after confirming no other full run of the same gate is still going, and if the same signature recurs, stop retrying and drop to the narrowest slice the foreground `timeout` param can cover instead, rather than a third attempt or a manual poll of the job's own PID once you've stepped away from it. When the full run cannot be observed reliably this way, prefer the narrowest run that still proves the change over a full-suite run whose completion you cannot observe.
     Apply the identical script preference, narrowest-first default and failure classification here; do not restate the full rule. If you start a gate and then abandon it before it finishes - because the check above, or a narrower gate's own result, already settles what it was going to prove - name in the review comment (step 5) what was started, why it was abandoned, and what evidence substituted for it; an abandoned run is not itself evidence of anything and must not be cited as if it had completed.
   - **A fix that satisfies a tool is not thereby proven correct.** Where a diff exists to satisfy a diagnostic - a lint rule, a type error, a warning - check that it achieves what the diagnostic was reporting, not merely that the diagnostic went quiet; a passing tool is not evidence on its own.
   - **A rework fixing a gating or ordering defect in one of several structurally parallel implementations is checked against its siblings before it passes.** When the defect under review is in one of several implementations sharing the same shape - two screens with the same timer gate, two render paths calling the same sync step in the same wrong order - passing the fix once the specifically-cited call site is corrected lets the identical defect ship unfixed in its siblings, to surface one review round at a time. Before passing such a fix, identify the other structurally parallel implementations (grep for the shared shape: the same gate check, the same call sequence) and confirm the diff addressed the defect class there too, not only the site an earlier review round named. If a sibling still carries the same defect, fail and name it - a reviewer names what they saw, never the whole class, unless asked to look for it.
   - Fast path: if the diff touches only `steps/*.md`, other `*.md` docs, or spec files - no runtime-code or test change (see the project's `CLAUDE.md`, read per step 2, for its layout) - verify lint. For a workflow-origin repo (a `workflows/*.md`/`steps/*.md` diff), run `lc workflow check --dir .` from the worktree as a cheap local confirmation. `--dir` does not run `simulate` or `describe --mermaid`; for those, rely on whatever CI job the repo runs for them, which `watch-ci`'s crossed gate already confirmed passed for the head SHA before this step was reached.
   - **A green suite is not evidence that the spec's named tests ran.** If the spec's Testing section names specific files or methods that must get coverage, diff that named list against the actual test diff explicitly - confirm each named file/method has a new or changed test, not just that the suite passed. A suite can stay green throughout while a named test was silently never written: the path it would have covered may be broken, and the green suite never reveals it on its own. Treat an unimplemented named test as a review finding like any other gap, not as something the green build already checked.
   - **A modified existing test's assertions are diffed against their previous form, and any change is checked against the spec, not read fresh as if newly written.** For every test that already existed and passed before this diff, and whose assertions the diff changes, read what it asserted before (the merge-base blob, or `origin/main` if the file predates this branch) against what it asserts now. If the new assertion matches behaviour the spec's Design or Acceptance actually asked for, it is a legitimate update - name it as such. If it does not, that is a reject: a diff that quietly rewrites a passing test to agree with the new code, rather than leaving it to fail until the code satisfies it, has disarmed a tripwire instead of tripping it, and a suite that stays green throughout never shows you this on its own. This is the complement of the bullet above (a spec-named test that should have been ADDED and was not) - that catches an omission, this catches a rewrite, and neither is visible from a green suite alone.
   - **No unreconciled test/step-def removal.** For every test file or step-def module this branch's three-dot diff shows as modified or deleted (not one it only added), compare per-file per-name occurrence counts between `origin/main`'s copy and this branch's tip - a deleted file recomputes every name it held to zero rather than being excluded from the comparison. Identify a named test/step-def unit the way `WORKSPACE/CLAUDE.md`'s `## Stack-specific gate and review risks` section (or its stated test-file convention) says this repo does it - never a bare textual grep for a declaration keyword, which collapses two identically-named units in different scopes (two classes, two modules) into one count and can mask one of them dropping to zero. If `CLAUDE.md` states no such convention, this check does not run - say so explicitly in the review comment (step 5) rather than silently treating a stack with no stated convention as having nothing to reconcile. Counts, not set membership - a same-named survivor elsewhere in the repo does not excuse an in-file drop. A name whose count dropped is a defect unless the applicable source names it: the feedback this pass is answering (the PR's comment/review thread), or the spec attached to this item, in any section (Acceptance, Out-of-scope, Design or Testing alike) - the source that authorizes a first-pass removal, since a first pass has no feedback thread yet - directly, or paired with a specific added name as an explicit rename/consolidation pair (every old name and the new one unambiguously named in that section's text, however it phrases the change, e.g. a Design entry giving the old name, its `file:line` and the rename to make). No fuzzy matching beyond that, never inferred from plausibility or diff size. This check runs on every pass, first pass included - unlike `write-code`'s own baseline capture, which only fires on a rework. A `.feature` file this branch modifies directly (not the common case for `write-code`'s target repos) is `review-features`'s identical `Scenario:`/`Scenario Outline:` method, not this one - do not duplicate it here. A defect found here is a bullet like any other under this step, folded into the existing fail path below.
   - **No `@wip` may remain on any scenario this item's feature PR introduced (bdd-driven only).** Look in the claim JSON's `.runs` for the entry whose `phase` is `feature`, and take its `pr` - the same record step 5 reads for this phase's own PR. If none exists, this item did not go through a feature phase (spec-driven, not bdd-driven) - skip this check. If one exists, list the `.feature` files it touched (`gh pr view <feature-pr-url> --json files -q '.files[].path'`) and grep each of those files' CURRENT content in this worktree for `@wip`. `implement-features` step 5 permits exactly one edit to a `.feature` file - removing `@wip` as a scenario goes green - and this repo may run its test suite with a marker deselecting anything still tagged (a marker or tag its own test runner supports), which silently excludes a leftover-tagged scenario from the run entirely: a coder who implements six of eight scenarios and leaves two tagged ships a green suite, a clean review, and a frozen contract that is a quarter inert. Any remaining `@wip` on one of those files is a reject.
   - **Every rule a workflow-origin diff adds to a step or workflow file is true for every user of that workflow.** Applies only when the diff touches `steps/*.md` or `workflows/*.md` of a workflow origin; otherwise tag it `not-applicable - not a workflow-origin diff`. A rule added in those files that names one language, framework, test runner, toolchain, repo, or the author's own environment is a reject: name each such line, and say where it goes instead - the target repo's `CLAUDE.md` when every contributor to that repo needs it, otherwise a guidance entry in the user's guidance repo with its `applies-to` facets and steps. This is a check, not a ban on words: a stack name inside an illustrative example that a generic rule is explaining is allowed when the rule itself holds for every stack.
   - **A hunk the spec does not straightforwardly authorise.** Each case below answers one question about the hunk, and states its own handling: does the spec disagree with itself, does it address the point without settling it, does it settle the point in a way you would override, or does it never mention the hunk at all. Pick the case by that question.
      - **An Acceptance bullet that contradicts an explicit, reasoned Out-of-scope or Design entry is a spec defect to route back, not a precedence call to make.** `spec-writer`'s "Acceptance is normative, narrative is illustrative" rule resolves an Acceptance bullet against an unremarkable walkthrough or design snippet - it does not license overriding a Design or Out-of-scope entry that states its own reasoning for a carve-out an Acceptance bullet's absolute phrasing collides with. Recognize the shape: Acceptance asserts an absolute ("no code path anywhere does X"), and Design or Out-of-scope elsewhere states, with reasoning, that one path intentionally still does X. That is not "Acceptance wins" - the spec disagrees with itself, and enforcing either side (demanding the code match the absolute, or waving the diff through on the strength of the exception) ships one half of a self-contradictory spec as settled. Any two spec sections that disagree are the same shape, not only Acceptance against Out-of-scope or Design: a worked example whose stated result the rule it illustrates does not produce, a Testing case that expects what Design says cannot happen, or a Sources row that contradicts the prose. Fail with a comment naming exactly which two sections conflict (for Acceptance against Design/Out-of-scope, which bullet and which entry), and route it back for the spec to state its own exception or resolve the conflict, rather than picking whichever side happens to read as normative.
      - **A hunk the spec is genuinely silent or ambiguous about is not a defect to fail over, when the coder's own commit body or PR description states the choice made and why, and you independently agree the spec does not settle it either way.** The spec addresses the point, states an intent the diff does not violate, and simply does not settle it precisely enough for two readings to converge. Failing a hunk like this to force a rework round does not produce a better answer - the next round either reverses the choice on no new information or restates the same defensible reasoning back, and either way the ambiguity is recorded nowhere: restated every round, in prose only the next agent reads. Two agents agreeing that something is unsettled is not a resolution: passing silently records it as settled, and failing over it manufactures a disagreement that was never real. Name it under a literal `Accepted differences:` line in the pass comment (step 5) instead - what the ambiguity is, what the diff does, and why the spec does not settle it - enough for a human reading this PR at `await-merge` to decide whether it is worth a follow-up item, without re-deriving the ambiguity themselves. Omit the line entirely when there is nothing to report under it - the same reasoning the `Also found, out of scope:` line below already rests on by only appearing when there is something to say.
      - **A reviewer's own general-quality standard is not grounds to override an explicit, reasoned spec carve-out - defer to the spec and record the disagreement instead.** The spec is not silent and does not disagree with itself - its Design or Out-of-scope section names the exact thing you would otherwise flag on general grounds (dead code, a naming convention, a missing test, or similar) and states its own reasoning for keeping or omitting it. What collides is your own general standard, not another part of the spec, and rejecting to force the code into line with it manufactures the same unbacked override step 5 already treats as a defect when it shows up in a diff: `review-code`'s own `rejected` edge routes only to `write-code`/`implement-features`, never back to a spec phase, so a coder acting on your reject cannot obtain the `spec-amendment` step 2 and step 5 already require for an override - it can only produce the exact unbacked override step 5's pass-path check exists to catch, one round later, with you as its author instead of its critic. Defer instead: pass the hunk as the spec's own reasoning decided it, and record your objection under a literal `Deferred to spec carve-out:` line in the comment (step 5) - what your standard would have flagged, and which Design/Out-of-scope entry decided otherwise - enough for a human reading this PR at `await-merge` to judge whether the carve-out still holds or is worth a follow-up item, without re-deriving your objection themselves. Omit the line entirely when you have no such objection - the same reasoning `Accepted differences:` and `Also found, out of scope:` already rest on.
      - **A hunk the spec does not authorize is not automatically a reject.** Before rejecting a change for spec-divergence, resolve the PR (the `pr` artifact per step 5, or `gh api "repos/{OWNER}/{REPO}/pulls?head={OWNER}:{BRANCH}&state=open" --jq '.[0].html_url // empty'` - `OWNER`/`REPO` from `git remote get-url origin` in WORKSPACE) and read its comment thread (`gh api` against issue comments, review comments, and reviews - the same surface `handle-feedback` reads) for a reply carrying `<!-- lc:decision=rework -->` - the marker `handle-feedback` step 4 posts when it queues a change as rework. If the hunk traces to such a reply, it is IN scope: judge it on its own merits - correctness, `CLAUDE.md` conventions, test coverage - exactly as if the spec had asked for it. "Not in the spec" stops being a defect in itself for that hunk. Split every hunk the spec does not authorise by whether it changes behaviour a user can see: output, a command's result or flags, stored data, an error a user meets, or a contract another component relies on. A user-visible hunk with no exemption is unexplained scope creep, reject it - such a change needs a spec or a human's request. A hunk that does not change user-visible behaviour (a refactor, logging, a tightened internal error path, an extracted helper, a test) never causes a reject: judge it on its merits and record it as a finding under the `Unspecced changes:` line in step 5. The exemptions nested under this case apply to user-visible hunks only. A hunk that traces only to a reply marked `<!-- lc:decision=answer -->` or `<!-- lc:decision=ignore -->` also has no exemption - unexplained scope creep, reject it. A reply with **no** decision marker at all predates this rule; judge that one case on its prose (a marker-less reply is not retroactively reinterpreted). If what you are rejecting also fixed a genuine, independently real defect the spec never asked about - not a stylistic aside - do not just delete it: capture it in the fail-path PR comment per step 5.
         - **A hunk that exists to keep THIS branch's own CI green is not scope creep, and is not gated on a PR comment.** `write-code` step 2's mandatory rebase onto `origin/main` can surface a regression the coder did not introduce - a pre-existing failure the branch inherits, or one the rebase itself exposes - and `write-code` step 4 requires naming it in the commit body: the specific failure it addresses and why the branch could not go green without it. Treat a hunk as exempt under this carve-out only when the commit body does so: read the body, and if it names a genuine CI-green fix, judge the hunk on its own merits - correctness, `CLAUDE.md` conventions, test coverage - exactly as for a hunk traced to a rework-queued comment. A user-visible hunk with no such explanation in the commit body has no exemption under this rule either: unexplained scope creep, reject it. As with any other acceptance check, verify the claim rather than take it on faith - confirm the failure the body names is real (the branch's own prior CI run, or reproducing it against `origin/main` before the rebase) before crediting the exemption.
         - **A stale comment and a provenance reply are separate questions - do not conflate them.** `watch-ci` step 4 already checks a comment's staleness (committer date vs `created_at`, since `git commit --amend` rewrites only the committer date) before this step runs. A comment's age does not tell you whether it is a rework-queued provenance reply, and a `<!-- lc -->` provenance reply is not stale merely for being old. If a comment reaches this step, judge its content and provenance at face value; do not re-derive staleness here.
   - Read each of these only when its precondition holds; otherwise tag it `not-applicable - <the precondition>` without reading the body.
      - **The spec names a companion repo and requires a PR there - confirm it directly in that repo before judging anything else.** The trigger is an explicit repo name, plus a stated requirement that a PR there must exist or merge alongside this one, stated in the spec's own prose - not a required marker syntax. Resolve the target: if the spec already names a specific PR url, use it directly. If it does not (the common case before that PR exists) and the spec names a specific companion item id, resolve that item's `pr` artifact (`lc show <that-id>`) the same way step 5 resolves this PR's own url. If the spec names neither a url nor an item id, search the target repo's PR list (`gh pr list --repo OWNER/REPO` / `gh api repos/{OWNER}/{REPO}/pulls`) for one whose body carries this item's marker `<!-- lc:item=<ITEM> -->` - the same marker `open-pr.md` step 6 writes into every PR body from the claimed item's id, so a companion PR following the same convention is findable by the same pattern (search bodies, e.g. `gh pr list --repo OWNER/REPO --state all --search '"lc:item=<ITEM>" in:body'`, never titles). Confirm the resolved PR exists and its state (open vs. merged) matches what the spec's landing-order language requires - a read-only `gh api`/`gh pr view --repo` call against the companion repo, no checkout, the same shape as every other `gh` call this step already makes against its own repo. Re-run this check itself on every pass, never trusting a prior pass's note, this pass's own memory, or the spec's prose alone as proof the companion PR is (still) in the right state - the companion repo's live state is what is authoritative, queried fresh every time this step runs, so a companion PR opened between a reject and the re-review is caught on the very next pass rather than surviving as a stale reject. A missing or wrong-state companion PR is a finding like any other under this step, folded into the existing fail path below - name exactly which companion repo/PR and what's missing or wrong about its state.
      - **A subagent produced a finding you are about to rely on - a finding you did not derive yourself is unverified until you check it.** If you fan out to parallel subagents on a large diff, their output is evidence, not a verdict. Before folding any specific claim into yours, independently confirm its most serious and most surprising citations - grep the file, read the lines. A false rejection built on a citation that does not exist costs a full rework cycle and teaches the coder to distrust the review.
