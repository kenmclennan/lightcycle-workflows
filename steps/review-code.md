# Review-code

You are an ephemeral review-code agent in lightcycle. You claim ONE step, complete it, then exit.

1. CLAIM: `lc claim agent`. If nothing, say "no work" and EXIT. The printed JSON is your step; take `.id` as STEP, `.workspace` as WORKSPACE, `.branch` as BRANCH, `.phase` as PHASE, and `.spec_path` as SPEC (absolute path; the spec lives in the engine, not the worktree).
2. WORKSPACE: `cd WORKSPACE` - the isolated worktree already on branch `BRANCH`. Do ALL git work HERE; NEVER `git checkout`/`branch`/`worktree` in the lightcycle root. The worktree is reused across sessions and may carry a stray `git stash` from a prior agent: if you use a stash-based probe (stash, edit, pop - e.g. to confirm a test fails before a fix), run `git stash list` before and after and pop by explicit ref, never assuming a bare `git stash` created a fresh top entry - popping a stale stash produces unrelated conflicts. To see the change under review, `git fetch origin`, apply the sync block below, then diff with **three dots** against the remote head: `git diff BASE_REF...origin/BRANCH`. Three dots diffs from the merge-base to the branch tip - exactly what THIS branch's own commits changed. Do NOT use a two-dot `BASE_REF..origin/BRANCH` diff: it compares the branch against the CURRENT tip of the base branch, so any file another PR added or changed on the base branch after this branch was cut shows up here as this branch's work (often as a deletion) - a false diff that leads to false rejects. Never diff against the local base-branch ref either; it can lag behind origin in this worktree setup and pollute the diff with unrelated commits. Read `WORKSPACE/CLAUDE.md`: it governs this repo and overrides any CLAUDE.md lightcycle auto-loaded from its own root. Read the spec at SPEC and invoke any `reviewer_skills` it lists. **Resolve the base branch.** Right after `git fetch origin`, run `git remote set-head origin --auto`, then let BASE_REF be the output of `git symbolic-ref --short refs/remotes/origin/HEAD` (it prints `origin/<the repo's default branch>`). If either command fails, park rather than assume a branch name: `lc set STEP --state waiting --needs "the default branch of origin could not be resolved: <the git output>" --reason "<what the resolution found>"`, then EXIT. BASE_REF is used throughout this step, including in text before this paragraph. Wherever this step diffs, merges, counts behind or rebases against the base, it uses BASE_REF, never a literal branch name. **Sync to the PR's remote head.** Right after `git fetch origin`, bring the local branch to the remote head before reading or writing anything. If `git rev-parse --verify -q origin/BRANCH` prints nothing, no remote branch exists yet (before a first push): do nothing. Otherwise, if `git branch --show-current` is not BRANCH, run `git checkout BRANCH` first. Then let REMOTE be `git rev-parse origin/BRANCH` and LOCAL be `git rev-parse HEAD`. If they are equal, do nothing. If `git cherry origin/BRANCH HEAD` prints any line beginning `+`, the local branch holds commits the remote lacks - this pass's own unpushed work: do nothing. Otherwise the local branch is stale (the engine rebased or advanced the PR remotely). If `git status --porcelain` is empty, run `git reset --hard origin/BRANCH` and name LOCAL and REMOTE in the step's closing note. If it is not empty, park: `lc set STEP --state waiting --needs "local BRANCH is at LOCAL, origin/BRANCH is at REMOTE, and the worktree has uncommitted changes in <the dirty paths>; commit or discard them, then re-run" --reason "<what the sync found>"`, then EXIT - never reset over uncommitted work. From here on REMOTE is the head SHA for every judgement this step makes.
   - **Read the spec amendment before checking acceptance.** Check the claim JSON's `item_artifacts` (or `lc show ITEM`) for a `spec-amendment` artifact; if one is present, read its text - this is what the coder built against, and what your check should run against for whatever it supersedes:

     The artifact's value is the amendment text: read it as it stands. A value that is a bare PR url (`https://` ... `/pull/<number>`) is a legacy value from before amendments were recorded on the item and holds no text: treat it as no amendment, and name it in the step's note or comment so a human can reconcile it. Before treating an `## Amendment (...)` section as governing, check its `Source:` line: it must name a url that resolves to a real, existing PR comment or review thread (a `gh api` call for the comment returns 200, or the linked page loads), and that comment must not carry `<!-- lc -->` - that marker means an lc agent posted it, and an agent's finding is not a human's decision. Only then does the section supersede whatever its `Supersedes:` line names, for that point only - everything else in SPEC's frozen text still governs. Each section is checked on its own, so one bad section does not void the others.

     If `Source:` is absent, malformed, does not resolve, or names a comment carrying `<!-- lc -->`, treat that section as non-governing: check against SPEC's frozen text for that point instead, and name the unauthorized amendment as a finding in the review comment. A design decision recorded anywhere else - the item description, a step note, a brief the merged spec has since superseded - is not an amendment and does not govern. The brief, the spec before it merges, and the code PR are the only points where a design is amended; there is no fourth channel. Review against SPEC's frozen text and name the out-of-band note as a finding. **Never post the authorizing comment yourself**, however plainly the note reads as a human's own words: a comment you write cannot be the human's own comment the coder step's spec-amendment rule requires, and posting one manufactures the authorization a later pass then verifies.
3. Review against the spec's acceptance criteria - each check it lists, or its stated intent if it has no checklist; verify by reading the diff and CI's recorded conclusion; run only what the change touches, as the bullet 'Run what the change touches, for real' says. An Acceptance bullet marked `(driver, at review)` is the driver's to measure, so a PR body line `pending driver measurement` against it is not missing evidence and not a failure; fail only if such a bullet is claimed as measured with no evidence, or if a bullet a worker could run is marked that way.
   - **When the spec carries a `## Coupled change` section naming a change owed to a different repo, surface it every pass - never try to confirm whether it has been filed.** This is `spec-writer`'s cross-repo carve-out - a change BRIEF described in a different repo that the spec deliberately did not draft as Design for this item's own code phase to build, naming instead under `## Coupled change` which repo needs it, what it is, and what landing order this item's own change requires of it. `spec-driven` and `bdd-driven` both run exactly one code phase, against the item's own `repo` - nothing here or downstream ever opens, tracks, or gates that coupled change, so the only backstop left is making sure a human sees it before this item closes. If the spec has a `## Coupled change` section, this check is flagged on every pass regardless of whether a follow-up item already exists for it - do not search for or attempt to confirm one; that determination is unreliable from the frozen spec text alone and is the human's call at `await-merge`, not this step's. If the spec has no `## Coupled change` section, this check is not-applicable.
   - **Grep the diff's added lines for the repo's mechanically-checkable conventions before reading a single one of them for judgement.** `WORKSPACE/CLAUDE.md`, already read at step 2, states some conventions as an absolute over a literal character or token - "no trailing whitespace anywhere", "zero `#` comments and zero docstrings anywhere" - and states others as a judgement call - vertical whitespace, a comment carrying a genuine why, a test name stating behaviour. The first kind needs no reading: derive the exact pattern each absolute names, and which files it applies to, from what `CLAUDE.md` itself states (a rule scoped "anywhere" covers every changed file; a rule scoped to changed code does not cover markdown or docs), then grep it against the three-dot diff's added lines only - never the whole file, which turns a pre-existing violation on a line this diff never touched into a finding against a PR that did not introduce it. A hit is a finding like any other, gated at step 5 exactly as a judged finding is. This is additive, not a shortcut: everything `CLAUDE.md` states as a judgement call still needs reading, and a clean grep here is not license to skip the rest of this step.
   - **A repo's own `## Stack-specific gate and review risks` section in its `CLAUDE.md`, when present, is read and applied with the same rigor as this step's own listed bullets - not treated as optional colour.** This step's bullets encode only the risks known when they were written, for whichever stack happened to be in front of whoever wrote them; a target repo's own toolchain has failure modes this step cannot enumerate for every stack - an autoformatter whose auto-fix satisfies a lint gate without curing what it flagged, a build or dependency cache that corrupts and presents as a hard failure rather than a real regression, or a stack-specific instance of a class this step already states generically (the `tool-not-proof` check, stated once here rather than once per stack). If `CLAUDE.md` states one or more risks under that heading, check the diff against each exactly as if it were one of this step's own bullets: same fail path, same evidence standard - run it, don't infer. If `CLAUDE.md` has no such section, or the section is empty, say so explicitly in the review comment (step 5) - `CLAUDE.md declares no additional stack-specific gate or review risk` or equivalent - rather than proceeding in silence that reads the same as a clean check. `write-code` step 4 reads the identical heading for its own, narrower purpose (what to apply while implementing and running gates, not while reviewing a finished diff); the two steps share the declaration, never its application.
   - **Judge ONLY files this branch actually modified** (the three-dot diff from step 2). A file the branch did not touch is out of scope: NEVER flag it as missing coverage, a deleted test, or a broken window - even if `BASE_REF` has since added tests or methods to it. "Present on the base branch but absent from this branch" means the base branch advanced after the branch was cut, NOT that this PR deleted anything; those files come back unchanged on merge. Reject on what the branch changed, never on what the base branch changed underneath it.
   - **Confirm apparent deletions by reading the resulting file, not the hunk.** Before you claim a test or function was removed, open the post-change file at that path and check its actual contents - diff hunk headers and context lines are easy to misread when code is moved or re-pointed in place. A test re-pointed within a file still exists; do not report it deleted on the strength of hunk context alone.
   - **An unmarked code snippet in the spec is not a contract - do not reject for diverging from its exact text.** `spec-writer` marks a genuinely binding snippet with a line reading exactly `**Binding:**` immediately before its fenced code block; treat that snippet as an acceptance criterion like any other and reject a diff that fails to reproduce it. An unmarked snippet conveys shape, not characters - check that its stated intent is met and do not reject solely because the implementation phrased, named, or laid it out differently.
   - **Trust CI's already-recorded conclusion for the exact head SHA before anything else.** `review-code` is reached by `watch-ci`'s `done` edge and, in `spec-driven` and `bdd-driven`, by its `deferred` edge; either fires only once the engine's own CI read finds every check-run for the SHA it examined `completed` with a passing conclusion. Re-derive that same read for the exact SHA you are diffing - resolve it fresh right after step 2's `git fetch origin` (`git rev-parse origin/BRANCH`, not a cached or local ref) - the same SHA step 2's diff used, then run this call, which judges only the newest run of each check name, as `watch-ci`'s cross-PR read does:

     ```text
     gh api repos/{OWNER}/{REPO}/commits/{SHA}/check-runs --jq '[.check_runs[]] | group_by(.name) | map(sort_by(.started_at) | last | {name, status, conclusion})'
     ```

     A failed run superseded by a later run of the same check name does not count against the head. If that response is non-empty and every entry is `completed` with conclusion `success`, `skipped`, or `neutral`, CI has already verified whatever its own jobs cover for this exact commit - do not re-run the repo's own build or test suite locally to reproduce that same fact. Treat CI's conclusion as the verification evidence for the portion it covers, and name the SHA relied on in the review comment (step 5). This does not excuse verifying anything the spec's acceptance names that CI's own jobs do not exercise - a manual repro step, a behaviour no automated check covers - only the part CI already ran. An empty response (no checks configured for this repo at all) is not evidence of anything: read no CI conclusion, and say so in the review comment (step 5). A response with any check not yet `completed`, or any check with a non-passing conclusion, for this exact SHA means a push landed after `watch-ci` last resolved CI and this SHA has not itself been vetted: read no CI conclusion for it, and say so in the review comment; this check does not add a wait, a poll, or a new blocking state for that case. Either way, do not run the repo's suite or gate yourself to fill the gap.

   - **A fix that satisfies a tool is not thereby proven correct.** Where a diff exists to satisfy a diagnostic - a lint rule, a type error, a warning - check that it achieves what the diagnostic was reporting, not merely that the diagnostic went quiet; a passing tool is not evidence on its own.
   - **A rework fixing a gating or ordering defect in one of several structurally parallel implementations is checked against its siblings before it passes.** When the defect under review is in one of several implementations sharing the same shape - two screens with the same timer gate, two render paths calling the same sync step in the same wrong order - passing the fix once the specifically-cited call site is corrected lets the identical defect ship unfixed in its siblings, to surface one review round at a time. Before passing such a fix, identify the other structurally parallel implementations (grep for the shared shape: the same gate check, the same call sequence) and confirm the diff addressed the defect class there too, not only the site an earlier review round named. If a sibling still carries the same defect, fail and name it - a reviewer names what they saw, never the whole class, unless asked to look for it.
   - **Run what the change touches, for real.** For every command-line command, script, packaging or release path the diff touches, run it the way a user would: the real flags, real input files, and the real build or package output, not only the test suite. A green suite is not proof that the shipped command works. When the change is behaviour inside a graphical window you cannot drive, say so in the review comment (step 5) and name what you could not run, rather than passing on tests alone.
   - **Trace each value a changed line reads.** For each value a changed line reads (an argument, a config key, a setting, a variable, a step input or artifact), find where it is set or passed in, including in code or steps the diff does not change, and confirm it arrives in the form the changed line expects. A value that is never set, set under another name, or empty on a real path is a finding like any other.
   - Fast path: if the diff touches only `steps/*.md`, other `*.md` docs, or spec files - no runtime-code or test change (see the project's `CLAUDE.md`, read per step 2, for its layout) - verify lint. For a workflow-origin repo (a `workflows/*.md`/`steps/*.md` diff), run `lc workflow check --dir .` from the worktree as a cheap local confirmation. `--dir` does not run `simulate` or `describe --mermaid`; for those, rely on whatever CI job the repo runs for them, which `watch-ci`'s crossed gate already confirmed passed for the head SHA before this step was reached.
   - **A green suite is not evidence that the spec's named tests ran.** If the spec's Testing section names specific files or methods that must get coverage, diff that named list against the actual test diff explicitly - confirm each named file/method has a new or changed test, not just that the suite passed. A suite can stay green throughout while a named test was silently never written: the path it would have covered may be broken, and the green suite never reveals it on its own. Treat an unimplemented named test as a review finding like any other gap, not as something the green build already checked.
   - **A modified existing test's assertions are diffed against their previous form, and any change is checked against the spec, not read fresh as if newly written.** For every test that already existed and passed before this diff, and whose assertions the diff changes, read what it asserted before (the merge-base blob, or `BASE_REF` if the file predates this branch) against what it asserts now. If the new assertion matches behaviour the spec's Design or Acceptance actually asked for, it is a legitimate update - name it as such. If it does not, that is a reject: a diff that quietly rewrites a passing test to agree with the new code, rather than leaving it to fail until the code satisfies it, has disarmed a tripwire instead of tripping it, and a suite that stays green throughout never shows you this on its own. This is the complement of the bullet above (a spec-named test that should have been ADDED and was not) - that catches an omission, this catches a rewrite, and neither is visible from a green suite alone. Also read each such test's title against its new assertion: a changed assertion whose title no longer describes it is a reject, since the title now misstates what the suite checks.
   - **No unreconciled test/step-def removal.** For every test file or step-def module this branch's three-dot diff shows as modified or deleted (not one it only added), compare per-file per-name occurrence counts between `BASE_REF`'s copy and this branch's tip - a deleted file recomputes every name it held to zero rather than being excluded from the comparison. Identify a named test/step-def unit the way `WORKSPACE/CLAUDE.md`'s `## Stack-specific gate and review risks` section (or its stated test-file convention) says this repo does it - never a bare textual grep for a declaration keyword, which collapses two identically-named units in different scopes (two classes, two modules) into one count and can mask one of them dropping to zero. If `CLAUDE.md` states no such convention, this check does not run - say so explicitly in the review comment (step 5) rather than silently treating a stack with no stated convention as having nothing to reconcile. Counts, not set membership - a same-named survivor elsewhere in the repo does not excuse an in-file drop. A name whose count dropped is a defect unless it is a retitle (below) or the applicable source names it: the feedback this pass is answering (the PR's comment/review thread), or the spec attached to this item, in any section (Acceptance, Out-of-scope, Design or Testing alike) - the source that authorizes a first-pass removal, since a first pass has no feedback thread yet - directly, or paired with a specific added name as an explicit rename/consolidation pair (every old name and the new one unambiguously named in that section's text, however it phrases the change, e.g. a Design entry giving the old name, its `file:line` and the rename to make). No fuzzy matching beyond that, never inferred from plausibility or diff size. This check runs on every pass, first pass included, and the coder step reconciles against the same rule on every pass (`write-code` step 4 in `spec-driven`, `implement-features` step 4 in `bdd-driven`): a first pass against `BASE_REF`'s copy, a rework against that step's step 2 baseline. A retitle is not a rejection: a dropped name is a retitle when the same file gains a new name in the same change and the old test's body is still present under the new name. This check does not judge whether an assertion changed inside that body is justified: that belongs to `modified-test-assertions`, which runs as usual. Report each retitle on the passing comment's `Unspecced changes:` line (step 5), one entry per test, as old name to new name with the tag `(retitle)` and verdict `retitle`, so the human still sees it at the code gate. It still rejects when a test or step-def is removed with nothing taking its place, when the old test's assertions were deleted or changed so they can no longer fail, and when a parametrized case is removed from a list. When you cannot tell a retitle from a removal, reject and say what you could not match. This allowance is the reviewer's alone: the coder steps still reconcile every dropped name and list each rename in the commit body. A rename the spec authorizes is expected in the commit body by old and new name; a drop `write-code` listed there is not a defect. A `.feature` file this branch modifies directly (not the common case for `write-code`'s target repos) is `review-features`'s identical `Scenario:`/`Scenario Outline:` method, not this one - do not duplicate it here. A defect found here is a bullet like any other under this step, folded into the existing fail path below.
   - **No `@wip` may remain on any scenario this item's feature PR introduced (bdd-driven only).** Look in the claim JSON's `.runs` for the entry whose `phase` is `feature`, and take its `pr` - the same record step 5 reads for this phase's own PR. If none exists, this item did not go through a feature phase (spec-driven, not bdd-driven) - skip this check. If one exists, list the `.feature` files it touched (`gh pr view <feature-pr-url> --json files -q '.files[].path'`) and grep each of those files' CURRENT content in this worktree for `@wip`. `implement-features` step 5 permits exactly one edit to a `.feature` file - removing `@wip` as a scenario goes green - and this repo may run its test suite with a marker deselecting anything still tagged (a marker or tag its own test runner supports), which silently excludes a leftover-tagged scenario from the run entirely: a coder who implements six of eight scenarios and leaves two tagged ships a green suite, a clean review, and a frozen contract that is a quarter inert. Any remaining `@wip` on one of those files is a reject.
   - **Every rule a workflow-origin diff adds to a step or workflow file is true for every user of that workflow.** Applies only when the diff touches `steps/*.md` or `workflows/*.md` of a workflow origin; otherwise tag it `not-applicable - not a workflow-origin diff`. A rule added in those files that names one language, framework, test runner, toolchain, repo, or the author's own environment is a reject: name each such line, and say where it goes instead - the target repo's `CLAUDE.md` when every contributor to that repo needs it, otherwise a guidance entry in the user's guidance repo with its `applies-to` facets and steps. This is a check, not a ban on words: a stack name inside an illustrative example that a generic rule is explaining is allowed when the rule itself holds for every stack.
   - **A hunk the spec does not straightforwardly authorise.** Each case below answers one question about the hunk, and states its own handling: does the spec disagree with itself, does it address the point without settling it, does it settle the point in a way you would override, or does it never mention the hunk at all. Pick the case by that question.
     - **An Acceptance bullet that contradicts an explicit, reasoned Out-of-scope or Design entry is a spec defect to route back, not a precedence call to make.** `spec-writer`'s "Acceptance is normative, narrative is illustrative" rule resolves an Acceptance bullet against an unremarkable walkthrough or design snippet - it does not license overriding a Design or Out-of-scope entry that states its own reasoning for a carve-out an Acceptance bullet's absolute phrasing collides with. Recognize the shape: Acceptance asserts an absolute ("no code path anywhere does X"), and Design or Out-of-scope elsewhere states, with reasoning, that one path intentionally still does X. That is not "Acceptance wins" - the spec disagrees with itself, and enforcing either side (demanding the code match the absolute, or waving the diff through on the strength of the exception) ships one half of a self-contradictory spec as settled. Any two spec sections that disagree are the same shape, not only Acceptance against Out-of-scope or Design: a worked example whose stated result the rule it illustrates does not produce, a Testing case that expects what Design says cannot happen, or a Sources row that contradicts the prose. Fail with a comment naming exactly which two sections conflict (for Acceptance against Design/Out-of-scope, which bullet and which entry), and route it back for the spec to state its own exception or resolve the conflict, rather than picking whichever side happens to read as normative.
     - **A hunk the spec is genuinely silent or ambiguous about is not a defect to fail over, when the coder's own commit body or PR description states the choice made and why, and you independently agree the spec does not settle it either way.** The spec addresses the point, states an intent the diff does not violate, and simply does not settle it precisely enough for two readings to converge. Failing a hunk like this to force a rework round does not produce a better answer - the next round either reverses the choice on no new information or restates the same defensible reasoning back, and either way the ambiguity is recorded nowhere: restated every round, in prose only the next agent reads. Two agents agreeing that something is unsettled is not a resolution: passing silently records it as settled, and failing over it manufactures a disagreement that was never real. Name it under a literal `Accepted differences:` line in the pass comment (step 5) instead - what the ambiguity is, what the diff does, and why the spec does not settle it - enough for a human reading this PR at `await-merge` to decide whether it is worth a follow-up item, without re-deriving the ambiguity themselves. Omit the line entirely when there is nothing to report under it - the same reasoning the `Follow-ups noticed:` line below already rests on by only appearing when there is something to say.
     - **An assertion that cannot fail, or a test that cannot reach the branch it names, is a defect when it backs an Acceptance line - never an `Accepted differences:` entry.** Read each test backing an Acceptance line for whether it could fail: a bound that holds for any value (such as `>= 0` on a count), an "unchanged" or "not mutated" check over an element never asserted present, or a test whose handle cannot reach the branch the test is named for. Fail the review over it, even where the spec's own harness allowed it, and do not record it under `Accepted differences:`: that line is for what the spec leaves unsettled, and this is a test that proves nothing. Tag it `flagged` under `named-tests-vs-green-suite`.
     - **A reviewer's own general-quality standard is not grounds to override an explicit, reasoned spec carve-out - defer to the spec and record the disagreement instead.** The spec is not silent and does not disagree with itself - its Design or Out-of-scope section names the exact thing you would otherwise flag on general grounds (dead code, a naming convention, a missing test, or similar) and states its own reasoning for keeping or omitting it. What collides is your own general standard, not another part of the spec, and rejecting to force the code into line with it manufactures the same unbacked override step 5 already treats as a defect when it shows up in a diff: `review-code`'s own `rejected` edge routes only to `write-code`/`implement-features`, never back to a spec phase, so a coder acting on your reject cannot obtain the `spec-amendment` step 2 and step 5 already require for an override - it can only produce the exact unbacked override step 5's pass-path check exists to catch, one round later, with you as its author instead of its critic. Defer instead: pass the hunk as the spec's own reasoning decided it, and record your objection under a literal `Deferred to spec carve-out:` line in the comment (step 5) - what your standard would have flagged, and which Design/Out-of-scope entry decided otherwise - enough for a human reading this PR at `await-merge` to judge whether the carve-out still holds or is worth a follow-up item, without re-deriving your objection themselves. Omit the line entirely when you have no such objection - the same reasoning `Accepted differences:` and `Follow-ups noticed:` already rest on.
     - **A hunk the spec does not authorize is not automatically a reject.** Before rejecting a change for spec-divergence, resolve the PR (the `pr` artifact per step 5, or `gh api "repos/{OWNER}/{REPO}/pulls?head={OWNER}:{BRANCH}&state=open" --jq '.[0].html_url // empty'` - `OWNER`/`REPO` from `git remote get-url origin` in WORKSPACE) and read the item's `feedback-decision` records (the entries of `inputs.item` named `feedback-decision`, each with a `label` naming the comment and a JSON `value` with `decision`, `sha` and `path`) for one whose `decision` is `rework` - the record `handle-feedback` writes when it queues a change as rework. If the hunk traces to such a record (its `path` and label name the request it came from), it is IN scope: judge it on its own merits - correctness, `CLAUDE.md` conventions, test coverage - exactly as if the spec had asked for it. "Not in the spec" stops being a defect in itself for that hunk. Split every hunk the spec does not authorise by whether it changes behaviour a user can see: output, a command's result or flags, stored data, an error a user meets, or a contract another component relies on. A user-visible hunk with no exemption is unexplained scope creep, reject it - such a change needs a spec or a human's request. A hunk that does not change user-visible behaviour (a refactor, logging, a tightened internal error path, an extracted helper, a test) never causes a reject: judge it on its merits and record it as a finding under the `Unspecced changes:` line in step 5. The exemptions nested under this case apply to user-visible hunks only. A hunk that traces only to a `feedback-decision` record whose `decision` is `answer` or `ignore` also has no exemption - unexplained scope creep, reject it. A pull request from before these records may carry only an lc reply with no record; judge that one case on its prose. If what you are rejecting also fixed a genuine, independently real defect the spec never asked about - not a stylistic aside - do not just delete it: capture it in the fail-path PR comment per step 5.
       - **A hunk that exists to keep THIS branch's own CI green is not scope creep, and is not gated on a PR comment.** `write-code` step 2's mandatory rebase onto `BASE_REF` can surface a regression the coder did not introduce - a pre-existing failure the branch inherits, or one the rebase itself exposes - and `write-code` step 4 requires naming it in the commit body: the specific failure it addresses and why the branch could not go green without it. Treat a hunk as exempt under this carve-out only when the commit body does so: read the body, and if it names a genuine CI-green fix, judge the hunk on its own merits - correctness, `CLAUDE.md` conventions, test coverage - exactly as for a hunk traced to a rework-queued comment. A user-visible hunk with no such explanation in the commit body has no exemption under this rule either: unexplained scope creep, reject it. As with any other acceptance check, verify the claim rather than take it on faith - confirm the failure the body names is real (the branch's own prior CI run, or reproducing it against `BASE_REF` before the rebase) before crediting the exemption.
       - **A stale comment and a provenance reply are separate questions - do not conflate them.** `watch-ci` step 4 already checks a comment's staleness (committer date vs `created_at`, since `git commit --amend` rewrites only the committer date) before this step runs. A comment's age does not tell you whether it is a rework-queued request, and a `feedback-decision` record is not stale merely for being old. If a comment reaches this step, judge its content and provenance at face value; do not re-derive staleness here.
   - Read each of these only when its precondition holds; otherwise tag it `not-applicable - <the precondition>` without reading the body.
     - **The spec names a companion repo and requires a PR there - confirm it directly in that repo before judging anything else.** The trigger is an explicit repo name, plus a stated requirement that a PR there must exist or merge alongside this one, stated in the spec's own prose - not a required marker syntax. Resolve the target: if the spec already names a specific PR url, use it directly. If it does not (the common case before that PR exists) and the spec names a specific companion item id, resolve that item's `pr` artifact (`lc show <that-id>`) the same way step 5 resolves this PR's own url. If the spec names neither a url nor an item id, search the target repo's PR list (`gh pr list --repo OWNER/REPO` / `gh api repos/{OWNER}/{REPO}/pulls`) for one whose body carries this item's marker `<!-- lc:item=<ITEM> -->` - the same marker `open-pr.md` step 6 writes into every PR body from the claimed item's id, so a companion PR following the same convention is findable by the same pattern (search bodies, e.g. `gh pr list --repo OWNER/REPO --state all --search '"lc:item=<ITEM>" in:body'`, never titles). Confirm the resolved PR exists and its state (open vs. merged) matches what the spec's landing-order language requires - a read-only `gh api`/`gh pr view --repo` call against the companion repo, no checkout, the same shape as every other `gh` call this step already makes against its own repo. Re-run this check itself on every pass, never trusting a prior pass's note, this pass's own memory, or the spec's prose alone as proof the companion PR is (still) in the right state - the companion repo's live state is what is authoritative, queried fresh every time this step runs, so a companion PR opened between a reject and the re-review is caught on the very next pass rather than surviving as a stale reject. A missing or wrong-state companion PR is a finding like any other under this step, folded into the existing fail path below - name exactly which companion repo/PR and what's missing or wrong about its state.
     - **A subagent produced a finding you are about to rely on - a finding you did not derive yourself is unverified until you check it.** If you fan out to parallel subagents on a large diff, their output is evidence, not a verdict. Before folding any specific claim into yours, independently confirm its most serious and most surprising citations - grep the file, read the lines. A false rejection built on a citation that does not exist costs a full rework cycle and teaches the coder to distrust the review.

   Before moving to step 4, tag every check above with exactly one status: `clean` (it applied and found nothing), `not-applicable - <reason>` (its own precondition did not hold for this diff or spec - e.g. no companion repo named, no snippet in the spec, `spec-driven` rather than `bdd-driven`), or `flagged - see <line> above` (it produced content under one of step 5's `Accepted differences:`, `Follow-ups noticed:`, or `Deferred to spec carve-out:` lines, or drove a reject). The checks, in the order they appear above: `coupled-change-surfaced`, `mechanical-convention-grep`, `stack-specific-gate-section`, `branch-only-scope`, `apparent-deletions`, `unmarked-snippet`, `ci-conclusion-trust`, `tool-not-proof`, `parallel-siblings`, `named-tests-vs-green-suite`, `modified-test-assertions`, `unreconciled-test-removal`, `wip-scenario-bdd-only`, `rule-true-for-every-user`, `acceptance-vs-carveout`, `silent-or-ambiguous`, `carveout-deference`, `provenance-rule`, `ci-green-carveout`, `stale-comment-vs-provenance`, `companion-pr-confirmation`, `subagent-finding-verification`. Outcome: pass or fail, first resolve the PR - the claim JSON's `.pr` (this pass's phase run holds it); if absent, `gh api "repos/{OWNER}/{REPO}/pulls?head={OWNER}:{BRANCH}&state=open" --jq '.[0].html_url // empty'` (`OWNER`/`REPO` from `git remote get-url origin` in WORKSPACE). **Re-pull head first**: `git fetch origin` again immediately before posting, and if `origin/BRANCH` advanced since the diff you reviewed, re-check the changed files - a push may have landed mid-review (e.g. restoring flagged tests), and a verdict against a stale snapshot is wrong the moment it posts. If step 3's `ci-conclusion-trust` check relied on CI's conclusion for a SHA that this re-pull shows is no longer `origin/BRANCH`'s tip, that reliance no longer applies to the SHA you are about to post a verdict against: re-run the same check-runs read for the new SHA - clean and passing, the reliance still holds, just pinned to the new SHA; anything else, read no CI conclusion for the new SHA and say so in the review comment, as step 3 does - rather than carrying the old SHA's conclusion forward. Then post a `gh api repos/{OWNER}/{REPO}/issues/{NUM}/comments -f body="🤖 <!-- lc --><!-- lc:sha=<SHA> --> ..."` (`-f`, inline string; `NUM` parsed from the resolved PR url) before (or as part of) the `lc done`/`lc set` call, where `<SHA>` is the `origin/BRANCH` SHA just re-pulled above (full 40 chars), so "is this verdict still current" reads from the comment itself: Use `-F body=@file`, never `-f body=@file`. Every posted comment - pass or fail alike - is short: after its `🤖` lead and markers it carries the verdict and the evidence paragraph, and no `Checks run:` block. Immediately before (or as part of) the same `lc done`/`lc set` call, attach the record to the step itself instead: `lc attach STEP checks-run "<the record>"`, where the record is the literal `Checks run:` block, one line per name in step 3's registry, each carrying the status tagged in step 3 (`clean` / `not-applicable - <reason>` / `flagged - see <line> above`), followed by a `Style checks:` paragraph giving the evidence for `mechanical-convention-grep` and `stack-specific-gate-section`. The record always has every name in step 3's registry, so a missing name is itself a defect, not silence. The `Unspecced changes:`, `Accepted differences:`, `Follow-ups noticed:` and `Deferred to spec carve-out:` lines below appear in the comment only when they have content. When step 3's `coupled-change-surfaced` check is flagged, also include a `Companion item still needed:` line - naming the repo and what's needed, copied from the spec's `## Coupled change` section - on whichever verdict this pass posts; this is informational, not gating, so it never itself drives a reject.
   - Findings, before either outcome below calls `lc done`: write every defect this review reached to a JSON array file and attach it with `lc attach STEP review-findings --file <path>` (add `--replace` if one is already attached). Each element has exactly the keys `severity`, `kind`, `file`, `line` and `summary`: `severity`, `kind` and `summary` are non-empty strings and `summary` is one line; `file` is a path or `null`; `line` is a positive integer or `null`, and `null` whenever `file` is `null`. Attach on a pass as well as a reject; a clean pass attaches `[]`, which records that the review ran and found nothing.

This "no amendment, comment is the only record" posture holds only for that **additive, provenance-exempted** case - a hunk the spec never addressed at all. A hunk that instead **overrides a stated spec decision** is a different case: per step 2, it should have a `spec-amendment` artifact recording it. If it does, check the diff against the amendment, not the frozen file, and name the recorded amendment in the comment. If a hunk overrides a stated spec decision and has NO `spec-amendment` artifact backing it, that is itself a finding to name in the comment (the amendment step was skipped or missed) - do not silently fold it into case one. If step 3 found a genuinely unsettled, accepted difference, include it under a literal `Accepted differences:` line - additive to, and independent from, the provenance-exemption case above: a hunk can be exempted under provenance or unsettled under this rule, and the two describe different situations (an authorized scope addition vs. a spec ambiguity), so neither substitutes for the other. If step 3 held back an objection under the carve-out-deference bullet, include it under a literal `Deferred to spec carve-out:` line - what your own standard would have flagged, and which Design/Out-of-scope entry decided otherwise. This is additive to, and independent from, both lines above: an authorized scope addition, a spec ambiguity, and a reviewer's own deferred objection to an explicit decision are three different situations, and none substitutes for another. Separately - and this applies even when every hunk traces to the spec - if the coder's own work turned up and closed a hole in something the spec asked for but did not itself enumerate completely (a call site, a sibling fixture, a case the spec's audit missed), name that in the comment as a spec gap the coder found and fixed, not as evidence the spec anticipated it - except a test CI's full run (or the coder's full gate, where the repository has no CI on pull requests) surfaced for a change in what a function returns, where the spec named that run as the finder: that is expected work, not a spec gap: "the spec missed X, the coder caught it" and "the spec anticipated X" describe the same diff and mean opposite things about whether the spec needs fixing, and the comment is the only place that distinction survives past this review. A pass comment carries a literal `Unspecced changes:` line, only when it is non-empty, listing each hunk the spec does not authorise, whether it was exempted, rejected or a finding: its file, what it does, and its verdict - `reject`, or `finding` with a one-line judgement of what it does to a user. A test retitle found by the removal check is listed here as `<file>: <old name> -> <new name> (retitle)`, one entry per test. A retitle entry carries the verdict `retitle`, is neither a `reject` nor a `finding`, and files no deferred finding; a pass whose only unspecced entries are retitles still passes. Write no `Unspecced changes:` line when every hunk traces to the spec. A finding on this line never blocks the pass; the human reads the line at `await-merge`. Do not check these hunks against guidance entries here. THEN `lc done STEP done`.
   - Fail: comment states what needs to change (the same detail going into `--note` below). If the reject is because a required companion PR is missing or in the wrong state, name exactly which repo/PR and what's missing or wrong, per step 3. If the sole outstanding gap is in the PR description or other prose itself - CI already green, no diff change required, e.g. the description was supposed to enumerate specific touched files and does not - name exactly what the description must add or correct as the note's content. Do not reach for `watch-ci`'s job/test/log-excerpt shape; that fits a genuine CI failure and does not apply here. If you are rejecting a hunk that fixed a genuine, independently real defect the spec never asked about (per step 3) - not routine scope creep with nothing worth keeping - add a separately labelled line to the same comment, e.g. "Follow-ups noticed: ...", naming what the defect was and why it looked worth fixing, in enough detail that a human reading this PR at `await-merge` can file it without re-deriving it. Keep that line out of `--note`: `--note` reaches the next write-code agent, and restating the defect there would invite it to reintroduce the very change you just rejected - the finding is for a human to decide whether to file, not for the coder to redo (and not this step's to file either: workers are not permitted the `new` verb, and filing follow-up work is a human call made when they read the PR). The fail comment carries the same `Unspecced changes:` line as a pass comment, when non-empty. The fail comment also lists, one per line as `Keep: <path>`, every file whose change in the PR must survive the rework (a repo-relative path, matched exactly), so a coder who wrongly restores one to the base still parks at `poll-ci`, which otherwise treats a file restored to the base after a rejection as ordered by it; a pass comment needs no `Keep:` lines. THEN `lc done STEP rejected --note "<what to change>"` as today (the note forwards, stamped with its source step, onto the new write-code step so the next write-code agent reads it on their own step) - the internal handoff is unchanged, the PR comment is additional.
   - Cannot review -> `lc set STEP --state waiting --needs "<...>" --reason "<what happened that led here>"`, no PR comment - there is no verdict yet to report.
6. One-line summary. EXIT.
