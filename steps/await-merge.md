# Await-merge (you + driver)

A PR is green, comments resolved, and rebased on the tip of main - ready to merge. You merge it, unless an active `lightcycle:autopilot` run's Scope Statement has explicitly granted the driver merge authority for this item - then the driver merges it directly, per that grant. The driver runs this skill either way, to set it up and record the outcome.

1. `lc show STEP`. The PR is on the phase run: take the `.runs` entry whose `pass` matches the step's `.pass` and whose `phase` is the one this gate sits in (`lc workflow describe <workflow>` names it), and open its `pr` on GitHub. A pass can have more than one run open at once, so match on both - `.pr` is on the claim JSON only, and `lc show` does not carry it.
2. Confirm CI is green and review comments are resolved; summarise the PR for the human.
   - **A `Companion item still needed:` line in `review-code`'s last comment means this item is not the whole job, even once this PR merges - say so plainly in the summary.** `review-code`'s `coupled-change-surfaced` check (`steps/review-code.md` step 3, LC-778) posts this line on every pass when the spec carries a `## Coupled change` section - a change BRIEF described in a different repo that no phase of this item's own workflow builds, tracks, or gates. It is easy to read a green, comment-resolved PR as "done" and merge past it: name the outstanding repo and what it needs directly in the summary to the human, rather than letting a complete-looking PR speak for the whole item. Applies wherever the review step immediately preceding this gate posts such a line - `review-code`'s `coupled-change-surfaced` check (`code-await-merge` in `spec-driven`/`bdd-driven`) or `review-workflow`'s equivalent (`code-await-merge` in `workflow-authoring`, LC-792) - other paths reaching this gate have no such comment to check.
3. The human merges it on GitHub - their call, their click - unless an active autopilot Scope Statement has granted the driver merge authority for this item (`lightcycle:autopilot`), in which case the driver merges it directly, having already confirmed in step 2 that it is green and comments are resolved.
4. The pool's PR monitor closes the item automatically once GitHub shows the merge; run `lc done STEP merged` yourself only if it has not caught up yet.
5. If it needs changes instead of merging, ask for them **on the PR**, not in the store: post a top-level comment mentioning the gate's feedback token (`@lc` in the built-in bundles - the `mention_token` hook on this node names it) saying exactly what to change and why. The pool's PR monitor spawns `handle-feedback`, which decides rework vs answer, replies on the thread carrying `<!-- lc -->` to record that decision, and routes this step for you. Do NOT run `lc done STEP changes` yourself while there is a PR to comment on - it skips the recorded reply, leaves the reviewer's reasoning where no reviewer will look, and never advances the comment ledger. Fall back to `lc done STEP changes --note "..."` only when there is no PR thread to post to.

The merge is the human's irreducible act, except where an autopilot Scope Statement has explicitly delegated it for this run; you assist and do the bookkeeping regardless.
