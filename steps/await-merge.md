# Await-merge (you + driver)

A PR is green and comments resolved - ready to merge. When the base requires up-to-date branches, the pool's monitor keeps the PR current with the base branch; otherwise it is current only as of the last coder pass and may be behind. If the head moves under the gate, the gate leaves and the PR returns through CI or its check, so it reaches you again only once it is green on the new head. You merge it, unless an active `lightcycle:autopilot` run's Scope Statement has explicitly granted the driver merge authority for this item - then the driver merges it directly, per that grant. The driver runs this skill either way, to set it up and record the outcome.

1. `lc show STEP`. The PR is on the phase run: take the `.runs` entry whose `pass` matches the step's `.pass` and whose `phase` is the one this gate sits in (`lc workflow describe <workflow>` names it), and open its `pr` on GitHub. A pass can have more than one run open at once, so match on both - `.pr` is on the claim JSON only, and `lc show` does not carry it.
2. Confirm CI is green and review comments are resolved; summarise the PR for the human.
   - **A `Companion item still needed:` line in `review-code`'s last comment means this item is not the whole job, even once this PR merges - say so plainly in the summary.** `review-code`'s `coupled-change-surfaced` check (`steps/review-code.md` step 3) posts this line on every pass when the spec carries a `## Coupled change` section - a change BRIEF described in a different repo that no phase of this item's own workflow builds, tracks, or gates. It is easy to read a green, comment-resolved PR as "done" and merge past it: name the outstanding repo and what it needs directly in the summary to the human, rather than letting a complete-looking PR speak for the whole item. Applies wherever the review step immediately preceding this gate posts such a line - `review-code`'s `coupled-change-surfaced` check (`code-await-merge` in `spec-driven`/`bdd-driven`) or `review-workflow`'s equivalent (`code-await-merge` in `workflow-authoring`) - other paths reaching this gate have no such comment to check.
   - **If the item has a `digest` artifact, read it and lead the summary with it.** The digest is the human's way in to a spec; the spec is the reference. No `digest` artifact means nothing to add here.
   - **If the Detail tab shows `in:deferred-findings`, file each finding as a standalone item before anything merges, and name them in the summary to the human.** The text is blocks headed `[<stage>]`, one dash-led entry per defect an agent found and chose not to fix; workers cannot file items, so this is the only place they surface. File each entry that is not already filed (the same text shows again at a later gate of the same item, so an entry you filed at an earlier gate is skipped), quoting the entry in the new item's description. If an entry should not be filed, say which and why in the summary. No `deferred-findings` means nothing to file here.
   - **Run every `Checked after merge:` bullet in the spec before anything merges.** If `lc show ITEM` lists a `spec` artifact, read it for Acceptance bullets that begin with the literal `Checked after merge:` (`spec-writer` marks the ones that need live data a build worker cannot read). Run each bullet's command, compare the result with its pass condition, and state each outcome in the summary to the human. A failed check is a reason not to merge: ask for changes on the PR as in step 5, naming the bullet and what the command returned. No `spec` artifact, or no such bullet, means nothing to run here.
   - **If the Detail tab shows `in:delivery`, lead the summary with its `Decision`; for a stack, list the layers from the claim's `stack_layers` with each layer's reason from its `Layer <n>` line.** `cut-delivery` writes `delivery` once, so it shows at every later gate of the item. No `delivery` means nothing to add here.
   - **For a stack, read the `poll-ci` step's `ci-not-run` artifact and hold any listed layer.** `lc show` on the item's `poll-ci` step lists the artifact, one line per layer whose build and tests did not run: `layer <n> of <m> <pr>: <labels>`. Name every listed layer in the summary to the human as "build and tests not run". Do not merge a listed layer until it has a CI run with those checks, which GitHub's cascade gives it once the layers below merge and it retargets onto the default branch. An empty or absent artifact means every layer ran the bottom layer's checks.
3. The human merges it on GitHub - their call, their click. Under the autopilot grant above, the driver merges it directly, having already confirmed in step 2 that it is green and comments are resolved. A stacked PR is merged with `gh stack merge <n> --squash --yes`, not `gh pr merge`, which GitHub refuses on a stack; `<n>` is the layer to merge up to, with everything below it included. Merging the top layer merges the whole stack, and the item closes through the merge hook. Merging only lower layers leaves the item at this gate: GitHub retargets the layer above, the engine re-reads that layer's CI, it notes the progress on the step, and the item closes once the top layer is merged. You may merge from the top or bottom-up, merging lower layers while the upper ones are reworked.
4. The pool's PR monitor closes the item automatically once GitHub shows the merge; run `lc done STEP <outcome>` yourself only if it has not caught up yet, where `<outcome>` is this gate's merge outcome: the one on the dashed `pr_merge: <outcome>` edge out of this stage in `lc workflow describe <workflow>` (`merged`, `spec-merged`, `features-merged`, `scenario-merged` or `no-change-merged`), which must also appear in `.valid_outcomes`. Never type `merged` by habit; most gates in a spec-first workflow do not have it.
5. If it needs changes instead of merging, ask for them **on the PR**, not in the store: post a top-level comment mentioning the gate's feedback token (`@lc` in the built-in bundles - the `mention_token` hook on this node names it) saying exactly what to change and why. The pool's PR monitor spawns `handle-feedback`, which decides rework vs answer, replies on the thread carrying `<!-- lc -->` to record that decision, and routes this step for you. Do NOT run `lc done STEP changes` yourself while there is a PR to comment on - it skips the recorded reply and leaves the reviewer's reasoning where no reviewer will look. Fall back to `lc done STEP changes --note "..."` only when there is no PR thread to post to.

The `--note` you leave when routing changes back, and any `--needs` or `--reason` text you park with, are read by a human or the next agent. They follow the standard below.
