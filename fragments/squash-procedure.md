Squash procedure. Before the reset, record the fork point: `FORK=$(git merge-base BASE_REF HEAD)`. Reset against that fork point, `git reset --soft "$FORK"`, never against `BASE_REF` directly: `BASE_REF` moves whenever another session merges, and resetting against it once it has advanced stages every intervening upstream commit as this branch's own diff, so the PR shows someone else's merged work as if this item wrote it - silently, with CI green and a plausible-looking diff. After the reset, run `git status` and confirm every file this pass changed is staged - `reset --soft` leaves the index at the old tree, not the working tree, so anything edited but not yet staged before the reset stays unstaged after it, and a plain `git commit` silently excludes it from the squash. Stage what is missing by explicit path, never `git add -A`/`git add .`.

Commit with a plain `git commit`, never `--amend`, after the reset: `HEAD` is then the base branch's own tip, so an amend rewrites an upstream commit and the PR opens carrying that commit's old message. The count `git rev-list --count BASE_REF..HEAD` cannot catch this - it still reads `1` - so after committing, check that `git rev-parse HEAD~1` equals `$FORK`, and stop the step if it does not. Then confirm the count is exactly `1` (or the required shape's own count): a staged index is not a commit, and the stage that opens the PR has nothing to open a PR from.

Once committed, for any file `git mv`d or renamed in this pass, diff `git show HEAD:<file>` against the working tree rather than trusting `git status`, which reports the rename and not whether the content matches, so a rename plus a later edit can squash with the edit silently dropped. Rebase over merge.
