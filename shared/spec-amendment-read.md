Check the claim JSON's `item_artifacts` (or `lc show ITEM`) for a `spec-amendment` artifact; if one is present and its PR is still open (`gh api repos/{OWNER}/{REPO}/pulls/{NUM} --jq .state` against `"open"` - `OWNER`/`REPO`/`NUM` parsed from `<pr-url>` itself, `https://github.com/{OWNER}/{REPO}/pull/{NUM}`; REST has no `"merged"` state string - a merged PR reads `state:"closed"` plus a separate `merged:true` field, so "still open" is `state == "open"`, case-changed from GraphQL's `"OPEN"` with no behavioural gap), read its current content - this is what the coder built against, and what your check should run against for whatever it supersedes:

```
git -C "$(dirname SPEC)" fetch origin <amendment-branch>
git -C "$(dirname SPEC)" show origin/<amendment-branch>:<relative-spec-path>
```

A read against refs, not a checkout - safe alongside other concurrent claims. Before treating an `## Amendment (...)` section as governing, check its `Source:` line resolves to a real PR comment/review thread (`gh api` returns 200, or the linked page loads) and that the comment does not carry `<!-- lc -->` - that marker means an lc agent posted it, and an agent's finding is not a human's decision. Only then does it supersede whatever its `Supersedes:` line names, for that point only; SPEC's frozen text still governs everything else. If `Source:` is absent, malformed, does not resolve, or names a comment carrying `<!-- lc -->`, treat that section as non-governing: check against SPEC's frozen text for that point instead, and name the unauthorized amendment as a finding in the review comment. If the amendment PR has since merged, this is a no-op - SPEC's own next-synced content already carries it. A design decision recorded anywhere else - the item description, a step note, a brief the merged spec has since superseded - is not an amendment and does not govern. The brief, the spec before it merges, and the code PR are the only points where a design is amended; there is no fourth channel. Review against SPEC's frozen text and name the out-of-band note as a finding. **Never post the authorizing comment yourself**, however plainly the note reads as a human's own words: a comment you write cannot be the human's own comment the coder step's spec-amendment rule requires, and posting one manufactures the authorization a later pass then verifies.
