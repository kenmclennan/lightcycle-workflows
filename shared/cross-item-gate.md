**BRIEF may also state a cross-item gate in prose - check it before finishing this step.** Wording that names another item as something this one must wait for or is gated behind ("gated behind `<item>`", "gate on `<item>` at activation", "blocked until `<item>` lands", or any equivalent - there is no one fixed phrase, so read for what BRIEF is actually saying, not a pattern match) is a live gate until checked. Where BRIEF names a concrete item id this way, resolve that item's own current state before doing anything more: `lc show <item>`. An item's `state` reaches `"done"` only through its own close path, never as a side effect of one of its own steps closing - treat the gate as released once, and only once, that reads `"done"`; a prose gate naming an item that has since closed is simply stale, and proceeding is correct. If it has not reached `"done"`, the gate is still live, and this check exists because nothing else may be enforcing it - whatever `--depends`/`lc dep` was or was not wired behind BRIEF's prose at filing time: park, `lc set STEP --state waiting --needs "<named item> must close first" --reason "<the gate BRIEF states, quoted>"`, then EXIT. Where BRIEF's gate language names no concrete item id, or `lc show` cannot resolve the id it names, there is nothing here to check mechanically; proceed.
