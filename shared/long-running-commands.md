Size the call: a run expected to take past about two minutes will hit the harness's Bash tool's own default timeout (120s) before it finishes, killing the run partway with no output at all - that kill is not a result and must not be read as one. Cover it with an explicit `timeout` param that comfortably covers it, or - once the expected duration exceeds that param's own ceiling (600000ms/10 minutes) - run it via the Bash tool's own `run_in_background` param instead; not a manual `&`/`disown`/`nohup` or a `sleep`-and-check loop, which can lose its output across a turn boundary. Never combine the two: passing a command that itself ends in its own trailing `&` as the argument to `run_in_background` detaches the real process from the one being tracked, so the task can report done while the real process keeps running unmonitored - a false success, and a worse failure mode than a false failure because nothing about it looks wrong. Pass the command directly, with no trailing `&` of your own. Run the gate so its own exit status survives - never pipe it into `tail`, `head` or a pager, and when output must be trimmed, set `set -o pipefail` first. Judge pass or fail by that exit status, never by how the last lines of output look. Quote the status (for example `exit 0`) in the closing note that reports the gate. A background run's status is the one its task notification or `TaskOutput` reports; a pipe to `tail` hides it in the same way.

Check on a backgrounded run before ending the turn that started it, rather than assume its result will resurface unprompted. Check it by its task id with the harness's task-output tool (`TaskOutput` with `block=true` and a long timeout), not by inspecting the output file or running `ps`/`pgrep`: a run you piped through `tail` or a pager yourself prints nothing until it exits, so an empty output file mid-run is what a healthy run looks like, not evidence it died. An output file that has stopped growing, or a process not visible from a fresh shell, is not evidence of a kill either: wait for the task notification or `TaskOutput` with `block=true`. A full gate can take 15 to 30 minutes on a contended machine. A `run_in_background` result that comes back with no output and nothing else to explain it is an infrastructure kill, not a completed result - retry once, but only for that no-output signal-exit signature and only after confirming no other full run of the same gate is still going, and if the same signature recurs, stop retrying and drop to the narrowest slice the foreground `timeout` param can cover instead, rather than a third attempt or a manual poll of the job's own PID once you've stepped away from it. When the full run cannot be observed reliably this way, prefer the narrowest run that still proves the change over a full-suite run whose completion you cannot observe.
